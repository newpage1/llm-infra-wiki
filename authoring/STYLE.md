# 文风规范（技术文档去 AI 腔）

这份规范是**给技术文档用的**，不是给公众号用的。它合并了三份来源：

| 来源 | 是什么 | 为什么用它 |
|---|---|---|
| [**de-slopify**](https://github.com/aiskillstore/marketplace/blob/main/skills/dicklesworthstone/de-slopify/SKILL.md) | 专门面向 **README 与文档**的去 AI 味 skill | 场景最对口：它管的就是 API 文档、README 这类文字 |
| [**Wikipedia: Signs of AI writing**](https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing) | 维基百科编辑社区维护的**实证清单**，每条都有外部研究支撑 | 维基百科正文就是参考类写作，和本站文体最接近；而且它区分「强证据」与「弱证据」 |
| [**stop-slop-zh**](https://github.com/VincentOld/stop-slop-zh) | 中文特有的 AI 腔（排比三件套、名词化、抽象主语） | 前两份是英文语境，中文的套话得看这份 |

**通用的「去 AI 味」教程不要照搬**：它们叫你「砍掉结构、加第一人称、段段讲故事」——
对本站**有害**。八小节骨架是刻意设计的，`路径:行号` 是立身之本。
本文末尾列了「**什么不该改**」。

---

## 一、最重要的一条：不要用脚本

de-slopify 里原话：

> You can't do this sort of thing using regex or a script, you MUST manually read each line
> of the text and revise it manually in a systematic, methodical, diligent way.

这不是洁癖。本站实测过：把「这也解释了为什么 X」批量换成「所以 X」之后，
出现了「**所以「为什么两条线都存在」**」这种自相矛盾的句子，事后得单独修 5 处。
**替换不是重写。** 遇到 `——`、「不是…而是…」时，正确答案通常是**重写整句**，
而不是换一个标点。

机械替换只适合两类东西：**罗列式的标签**（表格表头、公式化小标题）
与**纯删除**（删掉「真正的」「其实」这种不承载信息的虚词）。
判断这两类之外的任何一处，都要读上下文。

## 二、标志清单（按证据强度排序）

### 强证据

**① 破折号 `——` 过量**（de-slopify 列为第一号，Wikipedia 单列一节）

Wikipedia 原话：LLM 用破折号的频率高于同体裁的人类写作，而且**用法很程式化**——
「常模仿推销式写作，过度强调某个从句或排比」。

本站在第一次去 AI 腔后实测：正文 **2122 处 `——`，1.85 处/千字**。
这个密度是偏高的，是当前最值得处理的一项。

改法（按优先级）：

| 原来 | 改成 |
|---|---|
| `结论——理由` | `结论：理由` 或拆成两句 |
| `A——也就是 B` | `A，也就是 B` |
| `前半——补充说明` | `前半（补充说明）` |
| 一句话里两个 `——` | 至少去掉一个，通常是重写整句 |

**注意**：本站的 `——` 大量用在「结论 + 出处」这个位置（如
`不搬字节——真正的读交给 Transfer Engine`）。这是有信息量的用法，
**每段留一处是可以的**，要压的是密度，不是清零。

**② 「不是 X，而是 Y」类否定对举**（Wikipedia 叫 negative parallelism，列为典型 AI 标志）

Wikipedia：这类句子读起来像是在「纠正一个常见的误解」，仿佛读者先有了错的认识。
它承认人类也这么写，但**在 AI 输出里出现得显著更多**。

第一次处理时 188 处 → 15 处。剩下的都是**对比本身就是论断**的句子，保留是对的。

**③ 「值得注意的是」类强调虚壳**（de-slopify 与 stop-slop-zh 都列了）

已清零：值得注意 / 值得一提 / 不得不说 / 毫无疑问 / 需要指出的是。
后面跟的通常不是注意事项，而是一句正常说明——删掉引子，句子照常成立。

**④ 「真正的」当作强调**（中文特有）

已清零。「这层真正的开销在 X」删掉「真正的」不损失任何信息。

### 中等证据

**⑤ 粗体 `**` 过量**（Wikipedia 单列一节：Overuse of boldface）

Wikipedia 的说法：AI 会**机械地**给某个词或短语的每一次出现都加粗，
带着「key takeaways」的味道——这个习惯继承自 README、how-to、幻灯片。

本站实测 **6831 处，5.96 处/千字**——**这个密度明显偏高**，是仅次于破折号的一项。

但要区分两类：

| 该留 | 该压 |
|---|---|
| 表格里的标签（`\| **职责** \|`） | 整句整句的「结论加粗」（`**这既是它最重要的特征，也是最主要的阅读障碍**`） |
| 关键术语首次出现 | 同一个概念在多个小节反复加粗 |
| 排比项的领头词 | 一段里两处以上加粗 |

**改法**：一段最多加粗一处；能靠句式强调的就别加粗。

**⑥ 「三件套」排比**（Wikipedia 的 rule of three）

「A、B、C」三个并列是中文写作的舒适区，也是 AI 的。Wikipedia：
LLM 用它「让浅薄的分析看起来更全面」。

本站实测 1095 处「三X」。**但这里要非常小心**——大量是**事实性的**
（「三个控制器」「三条路径」「三个后端」），不是修辞。
只压**修辞性的三项排比**：三项换词说的是同一件事、或第三项只是把前两项换个说法。

**⑦ 元评论与推论腔**（de-slopify 的 "Here's why" 家族 + stop-slop-zh 的元评论）

已清零：这也解释了 / 这就是 / 这正是 / 一句话（公式化用法）。
de-slopify 把 "Here's why"、"Here's why it matters"、"At its core" 单列一节，
中文的对应物就是上面这些。

### 弱证据（仅作参考，不要单独据它改动）

- **标题层级、`---` 分隔线**：Wikipedia 列了，但技术文档本来就是这样组织的
- **列表格式**：本站在用 `- **小标题**：说明` 的行内标题列表，Wikipedia 把它列为 AI 标志之一
  （188 处，密度很低）。**结构性的分点不是罪**，见「什么不该改」
- **避免使用「是」**（copulative avoidance）：英文里是把 is 换成 serves as；
  中文对应物是名词化（见下），已经处理过
- **弯引号**：排版偏好，与 AI 无关

## 三、中文特有（来自 stop-slop-zh）

| 病灶 | 现在 | 改成 |
|---|---|---|
| 名词化 | 进行优化 / 做出选择 / 采取…措施 | 优化 / 选 / 直接写那个动作 |
| 模糊语气 | 其实 / 本质上 / 说白了 | 删 |
| 程度副词刷量 | 非常 / 十分 / 极其 | 删，或换「很」 |
| 八股连接词 | 首先 / 其次 / 综上所述 / 由此可见 | 删，让内容自己承上启下 |
| 假亲切 | 朋友们 / 家人们 / 让我们一起 | 删（本站从未出现，保持） |

## 四、不能碰的东西（改坏一个就前功尽弃）

| 不能碰 | 为什么 |
|---|---|
| `**读图**：` | 校验器要求带图小节的 html 里必须有「读图」 |
| `~~~` 围栏里的内容 | 要跟上游仓库源码逐字一致 |
| 所有 `路径:行号` | 本站的立身之本 |
| `%%标识符%%` 的名字 | 必须与代码里的名字一致 |
| SVG 里的结构属性 | 改坏 `lint_svg.py` 会报文字重叠 |
| 八小节顺序与标题 | 校验器强制 |

改的时候不要引入：`%%` 中间带 `%`、跨行粗体、表格单元格里的 `%%|%%`。

## 五、什么不该改（de-slopify 的 "What NOT to Fix"）

这几条很重要，它防止把技术文档改坏：

- **技术准确性**——不要为了文风牺牲正确性
- **必要的结构**——标题、列表、表格是内容的一部分
- **写清楚**——啰嗦不等于 AI 腔，把机制讲透是本文档的目的
- **代码与标识符**——焦点在正文散文，不在代码

具体到本站，**这些不算 AI 腔，不要动**：

- 八小节骨架（position → … → deps）
- 表格（本站明文规定「成表的内容必须画框线」）
- 「职责 / 边界」两行表——这是第一轮定的标准写法
- 「扩展点」——这是 vllm-ascend 页的主线概念，已给过定义
- 小标题（2060 个）——技术文档靠它跳读，密度正常
- 子代理汇报里那些「**认为不该改而保留**」的句子——对比本身就是论断

## 六、改完怎么验证

```bash
node tools/style_audit.js            # 看指标（含正文密度：破折号 / 粗体）
node tools/style_audit.js <分析页>    # 逐模块细看
bash tools/verify.sh                 # 结构 / 真渲染器 / 文风指标 / SVG
bash tools/verify-anchors.sh <页>     # 行号与逐字围栏（改过内容就跑）
```

两条守门指标：

- **锚点总数只许增不许减**——不能以丢掉「每句话指得到某一行」为代价
- **破折号与粗体的密度不许涨**——这两项是当前仅存的两个超标项

`tools/style-baseline.json` 是基线，`--guard` 会在 CI 里拦住回退。
