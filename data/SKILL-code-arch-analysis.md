# 模块代码分析

目标：产出一份文档，让读者**不必通读源码**就能上手这个模块 —— 知道它负责什么、
内部怎么分、关键抽象是什么、一次调用怎么走、哪里会踩坑。

判据只有一条：**读过这个模块源码的人看了，能认出自己的系统。**

### 这份 skill 怎么用

**先读 §0**（四条硬约束，决定了后面所有取舍），其余按需跳：

| 要做的事 | 去哪 |
|---|---|
| **先看**：四条不可协商的约束（图怎么画、锚点、钉版本、命名） | **§0 输出契约** |
| **动手之前**：划边界、找主干、提抽象 | **§1 分析流程**（七步，前三步没做完别开写） |
| **决定写什么**：模块页有哪几节、顺序如何 | **§3.0 模块页**（八节骨架） |
| **画图**：关系图 / 类图 / 流程图 | **§4 图**（含"先放图再解析图"的铁律） |
| **标来源**：观察 / 推断 / 未知怎么区分 | **§5 证据纪律** |
| **措辞**：去掉 AI 腔（破折号、对举、强调虚壳） | **§5.5 表达纪律** |
| **写插件类模块**（宿主 + 覆盖层） | **§6 插件式模块** |
| **写跨组件流程**（不属于任何单个模块） | **§7 跨组件联动** |
| **交稿前**：跑脚本 + 逐条自查 | **§8 校验清单** |
| **别踩的坑** | **§9 反模式** |

**引用相关的几条细则都在 §3.0 下面**（逐字抄、反引号 vs `%%`、围栏标记、路径写全、行号会过时）——
**它们有一个共同点：都是"别为了整齐而改写原文"。**

## 0. 输出契约（硬约束）

| # | 约束 | 为什么 |
|---|---|---|
| **C1** | **模块关系图必须是手绘 SVG**，不从代码生成，不用文本绘图 DSL | 生成的图是解析器视角：它画出解析到的每一条边，却画不出人理解的那个结构。模块图的价值在**取舍与分组**——你把谁放在谁旁边，是编辑判断 |
| **C2** | **类图用 PlantUML** | 继承/组合/聚合/依赖正是 PlantUML 擅长、SVG 笨拙的部分。分工不要搞反 |
| **C3** | **每个非显然的结论都指到 `path/file.ext:LINE`** | 读者必须能一跳证伪。无锚点的结论是传闻 |
| **C4** | **钉住分析版本**（commit SHA 或 release tag） | 代码在动。不钉版本，文档会静默腐烂，而读者无从判断哪段过期 |

> **C5**：**模块用代码里的真实标识符命名**，不要自造描述性短语。
> 读者在代码里搜「跨实例取数」是搜不到的，搜 `P2PBackend` 才是。
> 中文写在副标题里。

> C1+C2 的推论：**不要把 Mermaid 当默认选择**。它产出 C1 所禁止的那种无差别图，
> 也表达不了让架构图可读的空间分组（层、带、簇）。

## 1. 分析流程

**没有完成第 3 步之前不要开始写。** 最常见的失败是：对一个还没在整体中定位正确的模块，
写出了漂亮的细节。

### 第 1 步 · 划边界

先回答三个问题，**用一句话写下来**：

- 它负责什么？
- 它**不**负责什么？（同样重要——这是读者最容易误解的地方）
- 它和谁对话？输入从哪来、输出去哪？

边界划错的信号：找不到主干（见第 2 步），或者模块关系图里有一半的边指向外部。

### 第 2 步 · 找主干

找出那个**「一切都得经过」**的文件、类或函数——工厂、管理器、引擎类。
设计良好的系统通常**恰好有一个**。

找到它，剩下的阅读量会塌缩一个数量级。找不到？说明第 1 步的边界划错了，
或者这个模块实际上是三个模块。

```bash
# 谁被 import 最多
grep -rhoE '^\s*(from|import)\s+[a-zA-Z0-9_.]+' --include='*.py' . \
  | sed 's/.*[[:space:]]//' | sort | uniq -c | sort -rn | head -20
# 谁被引用最多（C/C++/Rust 同理，换符号）
```

### 第 3 步 · 先只读骨架

从**公开入口**往下读**恰好一层**，此时**只关心抽象，不关心实现**：

- 这一层有哪些类型？
- 它们之间是什么关系？
- 数据以什么形态在它们之间传递？

读完这一层就应该能画出模块关系图的**初稿**。画不出来就别往下读——
再读只会读到更多细节，而不会读到结构。

### 第 4 步 · 提抽象

对每个关键类型问：

| 问题 | 为什么问 |
|---|---|
| 它持有什么状态？ | 状态决定了并发模型和生命周期 |
| **谁拥有它？** 构造在哪、析构在哪？ | 决定组合 vs 聚合——类图上最容易画错的地方 |
| 它的生命周期是什么？ | 进程级 / 请求级 / 调用级，差别巨大 |
| 它是接口还是实现？ | 接口是扩展点，实现不是 |
| 它跨进程/跨设备吗？ | 跨边界的东西不能持有裸指针 |

### 第 5 步 · 追流程

挑 **1–3 条**承载了 80% 复杂度的操作，从入口走到设备/网络边界。每条记录：

- 调用链，**每个跨模块的跳**都带 `file:line`；
- 控制在哪里**跨进程 / 线程 / 设备 / 网络**——真正的复杂度都在这些地方，
  读者的默认假设也都在这些地方失效；
- 数据在哪里被**拷贝、序列化、注册、钉住**——这些是成本中心；
- **失败路径**，不只是顺利路径。

### 第 6 步 · 找约束

这一步最容易被跳过，也最需要经验。代码里有大量"隐含契约"：

- 断言（`assert`）——每一句断言都是作者写下来的约束；
- `NOTE:` / `WARNING:` / `TODO:` 注释——直接引用原文，作者说得比你好；
- 对齐要求、数量上限、区域限制（例如「最多 256 个注册区域」）；
- 配置项与默认值；
- 并发模型与同步原语；
- 版本要求（依赖的最低版本、ABI 约束）。

### 第 7 步 · 回验

拿你画好的模块关系图**逐框逐边**回查代码：

- 每个框对应真实文件吗？
- 每条边对应真实调用吗？方向对吗？
- 有没有代码里存在、但你图上没有的连接？

## 2. 要提取什么（问题清单）

| 维度 | 要回答的问题 | 产出 |
|---|---|---|
| **边界** | 负责什么？不负责什么？ | 一句话定位 + in/out of scope |
| **结构** | 分成几个子模块？依赖方向？ | **模块关系图（SVG）** |
| **命名** | 这些子模块在代码里**叫什么**？ | 用真实标识符命名的模块清单 |
| **抽象** | 关键类型有哪些？谁拥有谁？ | **类图（PlantUML）** + 所有权说明 |
| **状态** | 状态存在哪？生命周期？ | 状态与生命周期表 |
| **行为** | 主流程怎么走？在哪跨边界？ | 带锚点的调用链 |
| **接口** | 对外暴露什么？ | 接口表 |
| **扩展点** | 要改行为，实现哪个接口 / 注册哪个 hook？ | 扩展点表 |
| **配置** | 有哪些开关？默认值？影响？ | 配置表 |
| **约束** | 硬上限、对齐、版本要求 | 约束表（**引用代码原文**） |
| **失效** | 出错怎么办？重试/降级/回滚？ | 失败路径 |
| **性能** | 瓶颈在哪？什么条件下劣化？ | 质量属性表 |

> 最后两行是价值最密集的地方。读者花一下午能从代码里重建**结构**；
> 他们重建不出来的是**运行边界**——哪里会坏、上限在哪、哪些失败被处理了。

### 2.1 逻辑模块 ≠ 代码目录

按**能力**划分模块，而不是照搬目录结构：一个逻辑模块可以横跨多个目录，
一个目录也可能被拆进多个逻辑模块。

**但逻辑划分不等于自造名词。** 名字必须取代码里的真实标识符：

| 不要 | 要 |
|---|---|
| 跨实例取数 | `P2PBackend` |
| 显存 ↔ 主存搬运 | `NPUConnector` |
| 多硬件抽象层 | `platform` |
| KV 布局与算子 | `MemoryManager` / `KvFormat` |

理由很实际：**读者是拿着名字去代码里搜的。** 自造短语搜不到任何东西。

### 2.2 写机制，不写易变清单

逐条清单（某个文件的全部补丁点、全部配置键、全部函数签名）看起来详尽，
但它是**最易腐烂**的部分，而维护者恰恰最不需要它——他们可以自己 grep。

应当写的是：**类别、机制、和它们会怎么坏。**

| 不要 | 要 |
|---|---|
| 23 条补丁点全表（带行号） | 补丁的**四个类别** + 每类举 1–2 例 + 失败模式 |
| 全部配置项 | 会影响架构判断的那几个 + 默认值与影响 |
| 全部公开方法 | 承载设计的那几个 + 它们为什么这么切分 |

判据：**如果这段内容会因为一次常规重构而失效，它就不该出现在分析里。**

## 3. 文档结构

八节。**顺序是刻意的：整体 → 流程 → 细节。**
细节先行的文档是最常见的失败——读起来像逐行转述，而不是解释。

| § | 内容 | 何时可省 |
|---|---|---|
| 0 | **头部**：仓库、钉住的版本、分析日期、范围、**未覆盖什么** | 不可省 |
| 1 | **定位与职责**：解决什么问题；在系统里的位置；in/out of scope | 不可省 |
| 2 | **总体设计**：模块划分 + **模块关系图（SVG）** | 不可省 |
| 3 | **关键流程**：1–3 条主流程，带锚点的调用链 | 不可省 |
| 4 | **详细设计**：逐模块，**类图（PlantUML）** + 核心类/函数表 | ≤2 个模块时 |
| 5 | **接口**：对外 API、配置项、扩展点 | 非库时 |
| 6 | **硬约束与失效模式**：**运行包线**——上限 / 互斥 / 并发 / 失效。每条写成「条件 → 后果 → 该注意什么」 | 很少可省 |
| 7 | **问题与对比**：已知缺陷、可优化点、同类对比 | 可选但高价值 |

模板见 `references/analysis-template.md`。

### 3.0.00 铁律：宿主不写插件，插件可援引宿主（**单向**）

设 `%%A%%` 是宿主，`%%B%%` 是建立在 `%%A%%` 上的插件。**方向搞反就错了。**

| | `%%A%%` 的分析 | `%%B%%` 的分析 |
|---|---|---|
| 提到对方 | **一处都不提（连"另见"链接也不要）** | **可以、而且应当大段援引** |
| 为什么 | 宿主不认识自己的插件 | 插件不解释宿主就读不懂 |

**判据**：`%%A%%` 的源码里**有没有任何一行知道 `%%B%%` 存在**？
若没有，`%%A%%` 的分析里就不该出现 `%%B%%`——**包括术语、版本、仓库名、以及"另见 `%%B%%`"这类指针。**

**最容易漏的两类**：
- **拿 `%%B%%` 当比较对象**（「本组件在别处见过这种写法（`%%B%%` 的 X）」）
- **一行"另见"指针** —— 看起来无害，**但读者会以为 `%%A%%` 与 `%%B%%` 有关系**

**`%%A%%` 侧可保留**：`%%A%%` 自己的抽象、为扩展留的接缝、
设备枚举里的取值（例如 `%%"npu"%%` 作为 `%%device_type%%` 的一个合法值）。

#### 落地检查：`--cross`（**声明式，不靠自觉**）

```bash
node scripts/check_module.js data/analyses.js --cross
```

**插件在自己那份分析对象上声明两件事，宿主侧一个字都不用改**：

```js
pluginOf: 'lmcache',                          // 我建立在谁之上
aliasNames: ['lmcache-ascend', 'TokensHash', 'c_ops', 'cost_model', ...]
```

校验器拿这些名字（连同插件的 `id` / `title` / `repo`）去**宿主页的全部文字**里扫。
**三个方向都成立**：`A` 说了 `B` 的名字 → 错误；`B` 援引 `A` → 放行。

**别名要写"只属于 B 的东西"**：仓库名、包名、`B` 独有的类与模块。
**不要写含糊的词**（`Ascend`、`昇腾`、`npu`）——宿主自己的设备枚举里就有它们，
写进去只会制造误报。判据是：**这个词在宿主仓库里找不到，才归 `B`。**

#### 两类最容易漏的，机器只抓得住第一类

| | 例子 | 能不能自动抓 |
|---|---|---|
| **点了名字** | 「与 `lmcache-ascend` 的接口关系」 | **能**（`--cross`） |
| **没点名，但整段在讲它** | 「插件与宿主之间没有版本协商」「插件侧会有一个 `cost_model`」 | **不能**——要靠人读主语 |

**所以 `--cross` 通过不等于这条铁律就守住了。** 它只保证"没点名"。
**没点名的那种更常见，也更难发现**——判据仍然是那句：
**把每句话的主语读出来，问"宿主自己的源码知道这件事吗"。**

#### 本项目的真实错误（这条自动化就是这么来的）

LMCache 页的 `summary` 写着「因为 `lmcache-ascend` 正是插在这里的」，
`scope` 里有一条「与 `lmcache-ascend` 的接口关系」，`问题与风险` 里有两条整段在讲插件的版本策略。

**而当时的校验器一处都报不出来**——因为 `verifyIdentifiers` / `verifyPaths`
只扫 `section.html` 与 `blocks[].html`，
**模块级 `lead`、分析级 `summary` / `scope` 全在盲区里**。
那句 `%%TokensHash%%` 就藏在一个模块的 `lead` 里，躲过了标识符核对。

**现在检查已覆盖整页文字**（`lead` / `summary` / `scope` / `notCovered` / `table` / `chain`）。
**修完盲区，`TokensHash` 立刻被标识符核对报了出来。**

### 3.0.0 铁律：在那个模块，就只写那个模块的内容

**三层含义**：

1. **视角**——每句话的主语必须是本模块。
   写"与 X 的接合"时，要写成「**本模块的哪些部分在被 X 跟随**」，
   而不是替 X 做分析。
2. **术语**——不在本页使用别处定义的术语。要用就先定义。
3. **位置**——内容不能写进错误的模块。
   批量编辑时**同时匹配模块 id 与节 id**，替换后校验落点，并扫一遍重复。

**判据**：把每句话的主语读出来。不是本模块，就改写。

### 3.0 模块页：照搬业界 wiki 的六项

**不自创结构。** 骨架来自
[inkeep/open-knowledge 的 `codebase-wiki`](https://github.com/inkeep/open-knowledge)
——"把 DeepWiki 放进仓库"的成熟做法。它的分册：

```
OVERVIEW.md   枢纽：是什么 + 一张大图 + 导航
architecture/ 每个架构域一页：图 + 关键组件 + **背后的设计决策**
modules/      每个包 / 模块一页
flows/        端到端流程（深度足够时加 **Failure modes**）
concepts/     术语表
guides/       任务向："怎么改 X"
```

**本站**：`#/` 全景 · `#/a/<id>` 深度分析 · `#/a/<id>/<mid>` 模块页 · `#/flows` 联动分析。

**模块页的原文规定**：

> One page per package/module: **purpose, responsibilities, public API /
> entry points, key files, dependencies, and the flows it participates in.**

**对应成七节**：

| # | 节 | 出处 |
|---|---|---|
| 1 | **用途与职责**（含**不负责什么**） | purpose + responsibilities |
| 2 | **内部结构**（表 + 类图） | 由哪几块组成 |
| 3 | **公开 API 与入口** | public API / entry points——**只讲暴露出去的，内部用的一律不讲** |
| 4 | **关键流程** | flows it participates in——**必须配流程图** |
| 5 | **关键实现** | **挑复杂的讲**（分支 / 取舍 / 反直觉）+ **流程图**；**必须基于代码** |
| 6 | **关键数据结构** | **把结构体抄出来**（字段名 / 类型 / 每个字段为什么存在） |
| 7 | **关键文件** | **希望读者精读的文件**，按优先级排 |
| 8 | **依赖** | dependencies |
| — | **未覆盖**（文末小段，不是独立一节） | 覆盖边界 |

**顺序刻意：先讲清楚（1–4），再讲实现（5–6），最后给索引（7–8）。**

#### 两处**不要**放在模块页

| 内容 | 该放哪 | 依据 |
|---|---|---|
| **设计决策** | **`architecture/` 页**（本站的深度分析页） | 业界：architecture 页含 "the **design decisions** behind them"；**模块页规定里没有它** |
| **失效模式** | **`flows/` 页** | 业界：flows 页 "add a **Failure modes** section per flow" |

**为什么"设计决策"不该进模块页**：
分析者读的是代码，作者的取舍**无法从代码确证**；
而**"何时该重估"这种话，不该由分析者来说**。

**为什么"硬约束与失效模式"不该进模块页**：
**约束是跨模块的关系，失效是一条流程上的事件**——
**分别属于架构层与流程层**。

#### 3.0.1 顺序铁律：先讲清楚，再讲实现

**职责 → 内部结构 → 公开 API → 关键流程** 四节走完，
读者应当**不需要读源码就能说出**这个模块由哪几块组成、一次请求怎么流过。
**第 5 节（关键实现）才开始讲具体实现。**

反例（本项目真实出现过）：模块页第一节就贴出 `class PeriodicThread` 的代码。
**读者拿到的是一段实现，不是一张地图。**

详见 `references/module-template.md`。

**见 §5「证据纪律」**——那是这套规则的家，这里不重复。

#### 引用代码要逐字，不要为了整齐改写

**贴代码片段时，抄原文，不要"整理"它。**

本项目真实出现过的三种走样：

| 走样 | 例子 |
|---|---|
| **多行签名压成一行** | 真实是 7 个带类型标注的参数分 7 行，被写成一行 `tokens=None, hashes=None, ...` |
| **省掉实参** | 真实是 `batched_put(keys, objs, transfer_spec=..., location=...)`，被写成 `batched_put(keys, objs, self.store_location)`——**调用签名都变了** |
| **docstring 截成一行** | 多行 docstring 被合成单行 |

**为什么这不能忍**：读者会照着你的片段去理解接口。
**省掉的那个 `transfer_spec`，可能正是他排查问题时缺的那一环。**

**要省略就显式写 `...`**，让人一眼看出这里跳过了东西。

**校验器做两件事**（见 §8 的 `--repo`）：

1. **逐行核对**：正文里出现的每一行代码，仓库里必须找得到
2. **核对连续性**：一个代码块若没写 `...`，**它各行在源码里应当首尾相连**——
   不连续就说明你把散落各处的行拼在了一起，**读者按这个片段去搜会搜不到**

本项目真实案例：把三行的 `allocate(...)` 压成一行、
把带报错信息的 `assert` 截掉消息、把 6 行注释缩成 2 行——
**三种都被"连续性"这项查了出来**（逐行核对查不出，因为这些行**改写过**）。

**所以：要么逐字抄，要么显式写 `...`。**

#### 代码块里用反引号，不要用 `%%`

**这个站的渲染规则**（写别的站要按那个站的规矩来）：

| 位置 | 代码标记怎么写 |
|---|---|
| **正文（围栏外）** | **`%%X%%`**——反引号会提前终止 JS 模板字符串 |
| **代码块（`~~~` 围栏内）** | **反引号**——由 `fix_fences` 去掉；**`%%` 在围栏内不会渲染，会原样显示** |

**本项目真实犯错**：在围栏内的注释里写了 `%%finally`%%`，
**页面上就显示成字面的 `%%`finally%%`**。

**两种写法搞反了，两处都会坏**：围栏外用反引号 → 语法错误；
围栏内用 `%%` → 页面上露出 `%%`。
**校验器两条都查。**

#### 围栏要带语言标记——它决定这段是不是"引用"

**`~~~python` 和裸 `~~~` 在这个站里含义不同**：

| 写法 | 含义 | 校验器 |
|---|---|---|
| **`~~~python`** | **引用的源码**，必须逐字 | **逐行比对** |
| **裸 `~~~`** | **作者自己的记号**（编号清单、结构速写） | 跳过 |

**为什么必须分开**：本项目 `storage-backend` 有一段裸围栏，装的是
`1. PDBackend :132 config.enable_pd` 这样的**装配顺序清单**——
**它不是从代码里抄的，逐行比对只会报一堆假错。**（实测因此产生 25 处误报。）

**所以：凡是"从代码里抄的"，一律写 `~~~python`（或对应语言）。**
**不写标记，校验器就当它不需要逐字，等于自己放行了。**

#### 引用 docstring 与注释，也要逐字

**"抄代码"这条纪律同样适用于 `>` 引用块里的 docstring 摘录**——
**而这一类比代码围栏更容易漏，因为它不在围栏里。**

本项目真实翻车（藏了十轮才被肉眼发现）：

原文：`And the mask should ALWAYS be like FFFFFTTTTTTT, ...`
我写：`FFFFFTTTTTT`——**少抄了一个 T**，还把结尾的 "of the tensor" 丢了。

**为什么难查**：`FFFFFTTTTTT` 是 `FFFFFTTTTTTT` 的**前缀**，
**所以朴素的"字符串包含"判断会通过**。

**校验器的做法**：按标点切成子句，**每个子句都要能匹配，而且匹配处后面必须是词边界**——
**否则"少抄一个字符"这种错误永远查不出来。**

#### 交叉引用：有模块页的东西，提到时给链接

**模块之间是有关系的，不链就等于让读者自己去翻。**

**判据**：**这个名字在站内有自己的页面吗？**
有，就在**第一次提到**的地方给链接；没有（纯实现类）就不给。

**本项目实例**：「用途与职责」的"不负责什么"表里，
`GPUConnector` 链了、`TokenDatabase` 和 `StorageManager` 没链——
**但同一页的「依赖」节把它们都链了。同一页里两套做法，读者会以为后者不重要。**

**别过度链**：同一节里重复出现不必每次都链，
**代码块里的名字不链**（那是引用的源码）。

**本站的参考密度**：全部 20 个模块每千字 0–3 个链接，中位数约 1。
**engine 改之前是 0.2——明显偏低。**

**校验器会查坏链**（见 §8）：**每个 `#/...` 都要能落到真实目标上。**

#### 写路径要写全，别凭印象造一个

**"这个文件大概叫这个名字吧"是最容易犯、也最容易漏的错**——
**行号引用有校验，裸路径没有，所以它藏得最久。**

本项目在三处翻过车：

| 写的 | 真实的 |
|---|---|
| `~1600 行` | **2193 行**——数字凭印象写的 |
| `v1/storage_manager.py` | **`v1/storage_backend/storage_manager.py`** |
| `v1/gpu_connector.py` | **`v1/gpu_connector/gpu_connectors.py`**（是个包） |
| `v1/observability` | **`lmcache/observability.py`**（在包根，不在 `v1/` 下） |
| `%%move%%` / `%%compact%%` | **只有 `move`，没有 `compact`**——方法名也是编的 |

**两条纪律**：

1. **路径先在仓库里敲一遍**，别靠记忆。`git ls-tree -r --name-only HEAD | grep xxx`
2. **只写 basename 也可能不够**——本项目里 `base.py` 有 **19 个同名**、
   `observability.py` 有 **4 个**、`manager.py` 有 2 个。
   **同名多于一处的，必须写相对路径**，否则读者定位不到。

**校验器会查这两件事**（见 §8 的 `--repo`）：
**路径必须存在，且不能被同名文件模糊掉。**

#### 注释里的行号会过时——按方法名去找

**代码注释里出现「见某文件第 N 行」时，不要照抄那个行号。**

本项目实例：`cache_engine.py` 的注释写着
`# See pd_backend.py line 605 TODO comment.`，
**而 `pd_backend.py:605` 现在是一段 docstring 的结尾**。
真正的 TODO 已经挪到了 `:1058`。

**注释不会报错，行号会烂。**
**遇到这种引用，去目标文件里按方法名或关键词搜，写出你核实过的行号**——
顺便，**"注释已过时"本身就是值得写进文档的发现。**


### 3.9 铁律：先放图，再解析图

**每一处配图，都必须「图在前、文在后」。**

读者读图的方式与读文字不同：**图给整体，文字给细节。**
先写文字再补图，读者得先拼出模型再看图验证——**这是反的。**

**做法**：

1. 图紧跟在引出它的那句话之后，中间不隔段落
2. **图之后第一段必须是对图的解读**，而不是接着讲别的
3. **图中的每个元素都要在后文被解释到**（哪怕一句话）；
   **后文提到的图元也必须都在图里**
4. **按图的组织顺序解析**（左到右 / 上到下 / 按边），跳着讲会迫使读者反复扫图

**"读图"那段不是重复图的内容**——它解释**图为什么长这样**：
为什么是三块不是两块、为什么这条边是虚线、为什么这两框并列。

#### 怎么判断自己写的是"复述"还是"解读"

**复述**：把图里的框按顺序念一遍。**读者看完图就知道了，这段白写。**

**解读**：说出一件**从图上直接看不出来的事**。

**本项目真实的前后对照**（同一个位置）：

| | 写法 |
|---|---|
| **复述** | 「`%%store()%%` 有**三道提前返回**（健康、被动 rank、冻结），然后是**一个生成器循环**，最后**一次批量搬运**。」 |
| **解读** | 「这张图最上面是**三道并排的闸门**，而不是一个判断——**因为它们管的是三件不同尺度的事**：`%%is_healthy()%%` 管整个系统、`%%_is_passive()%%` 管这个 rank、`%%is_frozen()%%` 管这个时刻。**三个理由分属系统 / 副本 / 时间三个层面，所以不能合并成一个判断**——合并了就说不清是谁拦下的。」 |

**第二版多出来的信息**：这三道闸门**为什么是三个而不是一个**。

**另一种有效的解读角度：拿两张图对比。**
比如「`%%retrieve%%` 的图比 `%%store%%` 多了一个 `%%finally%%`——
**差别不在画法，在谁持有临时资源**」。**"图里少一个框"本身就是信息。**

#### 试过两次，这类"判断类"问题自动化不了

| 尝试自动化什么 | 结果 |
|---|---|
| 把图的元素按坐标排序，和源码出现次序比 | **一致度 10–23%，全是噪声**（注记框里的词不在流程顺序上） |
| 看读图段里有没有解释性连接词（因为 / 所以 / 而不是 …） | **词表窄了误报、宽了零信号** |

**两次都删掉了。判断类的问题靠人读——
但"人读"不是"凭感觉"：上面那张前后对照就是判断标准。**

**这条铁律的细则在各参考文件里不再重复**，一律以此处为准。

### 3.9.1 铁律：画完图，把框逐个拿回代码里对行号

**这条查不出自动化**（试过，启发式比对的一致度只有 10–23%，全是噪声），
**必须人工做，而且做得很快**：

1. **把活动图从上到下念一遍**，把每个框写成一行
2. **每个框去代码里找它对应的语句**，记下行号
3. **看行号是不是一路递增**——不递增的地方就是画错了

**重点查"提前返回"的位置**：它们最容易被画到后面去。

**本项目真实错误**（两张图同时画错）：

| 图 | 画成了 | 代码实际 |
|---|---|---|
| `retrieve` | 建 `ret_mask` → 判 `is_healthy` | **`is_healthy`(:808) → `ret_mask`(:836)** |
| `lookup` | 统计 → 判 `is_healthy` | **`is_healthy`(:1166) → 统计(:1173)** |

**根因是同一个**：健康检查是"最先返回"的那一步，
**但画图时容易顺手从"建变量"开始画**。

**顺带得到的发现**：三条路径都是 **`is_healthy()` 排在所有 `assert` 之前**——
**这不是巧合，是统一写法**。核对图序时会顺手发现这类横切规律。

### 3.9.2 铁律：总体设计图里的每个方框，下面必须有一个模块讲它

**"总分结构"不是修辞，是一条可执行的约束**：
**图里画了什么，下面就得有谁。** 否则读者顺着图往下找，找不到——
图在承诺一件正文没兑现的事。

**方向是单向的**（和 §3.0.00 同一条道理）：

```
总体设计图里的方框  ⊆  关键模块
```

**反过来不要求**——一个模块不必在图上有一个方框（它是某个框的下钻）。

#### 怎么做到可判定

**声明式，不用启发式**（启发式试过：图里所有标识符拿去模块正文里搜，
`LMCacheMPWorkerAdapter` 被判"有家"，因为它只是被别的模块**顺带提过**——
"提过"不等于"有模块讲它"，这正是这条规则要拦的东西）。

| 谁 | 写什么 |
|---|---|
| **每个模块** | `designSymbols: ['LookupModule', 'P2PController']`——**显式认领**它讲的那几个方框 |
| **整个分析** | `designUncovered: [{ sym, where }]`——图里画了、**但还没有模块**的方框 |

符号粒度是**方框标题**：SVG 里 `class` 含 `t-title-sm` 的 `<text>`。
**所以图必须用站点的类名**，否则校验器看不见它（也就等于没画）。

比对按**独立 token**：`P2P` 不会认领到 `P2PController` 上，
否则一条声明会顺手把两个框都占了。

#### 命令与三种违规

```bash
node scripts/check_module.js data/analyses.js lmcache --design
```

| 违规 | 判定 | 出路 |
|---|---|---|
| **方框无人认领、也没登记** | **错误** | 三选一：给它建模块 / 把框从图里删掉 / 登记进 `designUncovered` |
| **一个方框被两个以上模块认领** | **错误** | 读者会不知道该去哪看，必须定一个 |
| **模块认领了图里没有的符号** | 提示 | 声明过期了，改声明或补图 |

#### `designUncovered` 是临时状态，不是终点

**登记不等于解决。** 一个页面的总分结构算完成，
**是 `designUncovered` 为空的时候**——每个方框都有真正的家。

**本项目的真实错误**（这条规则就是这么来的）：LMCache 的 MP 架构图画了
`LMCacheMPWorkerAdapter`，而 integration 适配器那一块当时还挂在"待补"里——
**26 个方框里 6 个没家**，其中包括图上最显眼的那一格。

#### 这条规则会顺带发现图上多余的东西

**如果某个框死活找不到模块，通常不是"缺一个模块"，
而是这个框本来就不该画**——它可能只是背景、是别人的内部细节、
或者一个抽象名字而不是一个可分析的单元。**先怀疑图，再怀疑清单。**

## 4. 图

### 4.1 模块关系图 —— 手绘 SVG

**这是全文的中心。** 规则：

- **先在一条有目的的栅格上布局。** 先定轴（层？控制/数据？归属？），再把每个框放到格子上。
  对齐本身就是信息：**要比较的两个东西，必须同尺寸、同轴。**
- **用视觉分组，不只是位置。** 色带、底色、边框都在承载含义（"同属一层"、"这是热路径"）。
- **一个视觉通道只编码一个变量。** 颜色 = 子系统。边框 = 内部/外部。填充 = 热/冷。
- **每条边都要标注。** 未标注的箭头什么都没说。"调用"、"注册显存"、"读取 KV"
  是三种完全不同的关系。
- **内联进文档。** `<svg>` 可缩放、跟随 CSS 变量换主题、能在 git 里 diff。提交的 `.png` 三样都做不到。
- **控制细节量。** 一个框需要超过约 6 个词才能说清，那它是两个框，或者该配说明文字。

可复用图元与布局配方见 `references/svg-diagrams.md`——**从它开始，不要从空白画布开始。**

### 4.2 类图 —— PlantUML

- **只画当前模块的类**，加上它实现的接口，以及让形状可读所必需的一两个协作者。
  画全仓库的类不叫类图，叫目录列表。
- **箭头语义必须对。** 这是类图的全部意义：
  `<|--` 继承、`*--` 组合（拥有，生命周期绑定）、`o--` 聚合（持有，不拥有）、
  `-->` 关联、`..>` 依赖、`..|>` 接口实现。
  **把组合和聚合画反，比不画这张图更糟。**
- 基数（`"1" *-- "0..*"`）是设计的一部分时才标。
- 只注释那两三个承载了设计的类。
- 控制在 ~15 个类以内，超了就按模块拆。

语法速查与实例见 `references/class-diagrams.md`。

### 4.3 流程

**「关键流程」小节 = 一张图 + 一份带锚点的编号链。** 图给关系与顺序，编号给位置。

图省不掉：读者要先在脑子里装下一张地图，才读得动后面几十行 `路径:行号`。
但**图型要跟着内容选**，不要所有流程都画成分层框——

| 这一节真正要讲的东西 | 用哪种图 |
|---|---|
| 一次调用**依次经过谁**（跨进程 / 跨线程 / 跨设备） | **时序图**：参与者画成竖向泳道，时间自上而下，箭头带编号 |
| **有判定分支**（命中 / 未命中、能力够不够、失败怎么办） | **流程图**：菱形判定 + 条件标注 + 各出口 |
| **数据形态在变**（shape / dtype / 布局 / 地址表示） | **变换前后对照**：左右同轴并列，逐项可对 |
| 一次调用的**调用栈**，很浅且无分支 | 编号 + 锚点的树状清单（见下），可以配一张小图 |
| **谁拥有什么、分成几层** | 分层带——**只有这一种情况才用** |

判据很简单：**把图遮住，这一节的结论还成立吗？** 如果结论就是「顺序是这样」「分支在这」
「形状变成了那样」，那图本身就是结论，必须画；而且画错类型（比如用分层框表达时序）
就等于没画。

调用链的树状清单长这样，编号与图上的编号**必须能对上**：

```
handle_request()                api/server.py:120
 └─ Engine.submit()             engine/core.py:88
     ├─ Scheduler.schedule()    core/sched/scheduler.py:427   ← 决策点
     └─ Executor.execute()      executor/abstract.py:55
         └─ Worker.run()        worker/gpu_worker.py:210      ← 跨入设备
```

几条容易做砸的地方：

- **图要有信息量**：标出参与者、数据在哪一段内存（显存 / pinned CPU / 对端）、
  调用方向、步骤编号。几个空框配两条线不算图。
- **先图后文**：图放在小节开头，图下才展开。别把图夹在段落中间。
- **一条主流程一组图 + 分段解析**。流程长就拆成多个「块」（每块一张图 + 自己的解析），
  不要硬塞进一张图；块的 `lead` 里若写了「N 块 / N 图 / N 步」，改了块数要同步改 lead
  （校验器会查这一条）。
- **每段解析写「做什么 / 为什么 / 漏了会怎样」**，而不是复述代码。
- 图上出现的每个编号，正文里都要有对应的段落，并且那一段要带真实 `路径:行号`。

## 5. 证据纪律

**你读的是代码，作者的设计意图未必写下来。所以每条断言都要标明来源。**

| 来源 | 怎么写 |
|---|---|
| **代码注释 / docstring 明说** | 直接引用，标 `path:line` |
| **从代码结构可强推** | 「代码把 A 与 B 分开，而 A 需要 B 的 X，**因此**…」——**给出推理链** |
| **只是你的猜测** | 标为推断，**并写出能证伪它的观察** |

**宁可写「代码里没解释，但从 X 与 Y 的配合看只能是这个原因」，**
**也不要写成「作者显然是为了…」**——后者是把猜测包装成事实。

**这三个档次对应三种语气，混在一起是分析失去可信度的主要方式**：

- **观察到的**——你在代码里读到的，带锚点
- **推断的**——你对"为什么这样"的建模，标明是推断
- **未知的**——你确定不了，直说，不要糊过去

**另外两条**：

- **锚点打在边界上**，不是每一行都打
- **引用代码自己的警告**：断言、`NOTE:`、`raise` 的消息，
  往往比你能写的任何话都精确，**直接引用**

#### 「解释原因」与「编造动机」的分界

**不是不能写原因——是不能写没有依据的原因。**

| 句式 | 判断 |
|---|---|
| **「之所以 X：Y」** | **Y 就是依据**，只要 Y 是观察得到的事实，**这样写是好的** |
| **「X，因为 Y」** | 同上——只要 Y 指得到代码 |
| **「X 比 Y 更省事 / 更合理」** | **危险**——这是在替作者下判断，**代码里读不到** |

**本项目真实案例**（同一个位置，我第一版写错了）：

| | 写法 |
|---|---|
| **编造动机** | 「`%%EventManager%%` 只有一个实现，**自己 new 比注入更省事**。」 |
| **观察 + 标明推断** | 「`%%EventManager%%` 只有一个实现、**没有子类、也没有对应接口**——**"能被替换"这个前提在这里不成立**。（**代码里没有说明为什么选择自建**；上面这句是从"没有接口"推出来的，不是注释里写的。）」 |

**第二版多了什么**：**承认代码没说**。
**"更省事"是我替作者想的；"没有接口"是我读到的。**

**一个立即的判据**：**这句话里的形容词，删掉之后结论还成立吗？**
「更省事」删掉，结论就没了——**说明它是结论的全部，而它没有依据**。

**试过自动化，失败了**：拿"为了 / 省事 / 显然 / 之所以"这类词做全文扫描，
**20 个模块报 18 处，其中 16 处是「之所以 X：Y」这种完全正确的句式**。
**这个词表分不出"有依据的原因"和"编造的动机"**——**所以它靠人读。**

## 5.5 表达纪律：去掉 AI 腔

**§5 讲的是"别断言你证不了的东西"，这一节讲"别把证得住的东西写得像 AI 生成的"。**
两者都会让读者低估整篇的可信度，但成因不同：前者是证据问题，后者是表达问题。

### 为什么值得单列

读者对 AI 腔有很强的嗅觉，而**它一旦被认出来，你辛苦锚的每一行都会被一起打折**。
更重要的是：**这一节的多数条目有外部研究支撑，不是审美偏好。**

### 证据最强的几条

| 标志 | 依据 | 本项目实测（改前） |
|---|---|---|
| **破折号过量** | de-slopify 列为文档类写作的**第一号**标志；Wikipedia 单列一节，说 LLM 用得「程式化、pat way」 | 正文 2122 处 / 3.59 每千字（正常技术写作约 0.5–1） |
| **否定对举**「不是 X，而是 Y」 | Wikipedia 的 *negative parallelism*：承认人类也这么写，但在 LLM 输出里显著更多 | 188 处 |
| **强调虚壳** 值得注意的是 / 真正的 / 其实 / 本质上 | 删掉后句子照常成立 | 49 / 330 / 31 处 |
| **元解释腔**「这也解释了为什么…」（英文的 *Here's why* 家族） | de-slopify 单列一节 | 20 处 |
| **粗体机械强调** | Wikipedia 单列一节（*Overuse of boldface*）：AI 会给某个词的每一次出现都加粗，带「key takeaways」味 | 6827 处 / 11.5 每千字 |

> **中文还有自己的一套**：排比三件套（「是…是…更是…」）、名词化（「进行优化」
> 「做出选择」）、抽象主语（「时代要求我们」）。见 stop-slop-zh。
>
> **但"三项排比"要非常小心**：中文里大量「三个控制器」「三条路径」「三个后端」是
> **事实性的**，不是修辞。只压那种三项说的是同一件事、第三项只是把前两项换个说法的。

### 铁律：不要用脚本改措辞

de-slopify 的原话：**"You can't do this sort of thing using regex or a script,
you MUST manually read each line of the text and revise it manually."**

这不是洁癖，是实测。**本项目踩过的坑**：批量把「这也解释了为什么 X」换成「所以 X」，
结果是「**所以「为什么两条线都存在」**」这种自相矛盾的句子，事后单独修了 5 处。
同一轮还撞出过「所以 reaper 为什么要跑两遍」——「所以」和「为什么」互相打架。

**替换不是重写，而正确答案通常是重写整句。** 机械替换只适用于两类：

- **罗列式的标签**——表格表头、公式化的小标题
- **纯删除**——删掉不承载信息的虚词（「真正的」「其实」）

这两类之外的每一处，都要读上下文再落笔。

### 破折号怎么改（数量最大的一类）

先看用法是不是**程式化**——如果多数落在同一个形状上（本项目是 725/2122 处都是
「`**结论**——解释`」这一个公式），那本身就是「pat way」的证据。

| 原来 | 改成 | 判据 |
|---|---|---|
| `结论——它/这/那是/所以/因为…` | `结论。它/…` | 破折号后面是**完整句子**（有自己的主语谓语）→ 拆两句 |
| `结论——解释`（名词性） | `结论：解释` | 后面是列举、定义、或对前面那个名词的解释 |
| `A——补充说明` | `A（补充说明）` | 补充说明是插入语 |
| `A——B`，两边说同一件事 | 删掉一边 | 复述 |
| 一句里出现两个 `——` | 至少去掉一个 | 通常要重写整句 |
| `——也就是说 / ——换句话说` | `，也就是说 / 。也就是说` | 连接词不该用破折号 |

**每段最多留一处**——留的那处应当是「括号太轻、逗号太粘」的场合。
**表格里表示「无」的 `——` 不要动**，改标点会变义。

### 什么不该改（与上面同等重要）

这一条防止把好文档改坏：

| 不该改 | 为什么 |
|---|---|
| **技术准确性** | 不为文风牺牲正确性 |
| **必要的结构** | 标题、列表、表格是内容的一部分；八节骨架更是这个 skill 刻意设计的 |
| **写清楚** | 啰嗦不等于 AI 腔，把机制讲透是本 skill 的目的 |
| **对比本身就是论断的句子** | 如「MLA 的 prefill 与 decode 不是两种配置，而是两种数学」——改软反而丢信息 |

### 让它可测量

**靠自觉的规范会慢慢失守。** 建议给项目配一个可执行的体检，并把结果接进 CI：

1. **数几个固定腔调**——只统计**正文**：排除代码围栏、手绘 SVG、行内代码、`path:line`
   （不排除的话，代码里的 `%` 和 `**` 会把数字搞乱）
2. **加上密度指标**——破折号 / 粗体按千字归一。**绝对值没有意义**，页面大小不同
3. **一条守门指标：锚点总数（`path:line`）只许增不许减**

第 3 条是关键：**文风可以改，但不能以丢掉"每句话指得到某一行"为代价。**
没有这条，去 AI 腔会不知不觉退化成删句子——删掉带锚点的论断，指标好看了，文档废了。

> 密度不能逐模块相加再平均：要**先累加分子分母、合并完再算**。
> 本项目第一版直接加密度，算出了 332/千字这种荒谬数字。

## 6. 插件式模块

当模块是宿主（host）之上的**覆盖层**（monkey-patch、子类、适配器、跟随上游的 fork）时，
单独分析它是没有意义的——一半行为在宿主里。

必须做的：

1. **明确关系形态**——patch / 子类 / 适配器 / vendored fork。四者的升级成本完全不同。
2. **枚举替换点。** 对 patch 式插件这literally是一张表：
   `hook → 目标 → 改了什么 → 为什么必须改`。**这张表通常是整篇文档最有价值的产物**，
   因为它就是两个平台之间的 diff。
3. **区分"原样继承"与"被改写"。** 读者脑子里已经有宿主的模型，得告诉他哪些还成立。
4. **同时读两份代码**，标出流向被改道的位置：
   `host.py:120 → (patched) plugin/impl.py:44`。
5. **记录版本耦合**：对照上游的哪个版本、升级时要重新验证哪些 patch 点。

展开见 `references/plugin-and-cross.md`。

## 7. 跨组件联动（它不属于任何单个模块）

一次操作横跨多个独立项目时，**单独成篇**，不要塞进任何一个参与者的文档里。

- 放到平级的独立集合（如 `analysis/flows/`），并**双向互链**：组件页列出它参与的链路，
  链路页链回各组件。
- 结构：**拓扑 → 控制面 vs 数据面 → 逐段展开 → 失败路径**。
  **每一节都是「先图后文」**：图放节首，下面是分段解析，段段带 `file:line`。
- **图的类型要匹配那一节**：拓扑用连线图、控制面用时序图、数据面用泳道图、
  失败路径用分支图。**七节画成七张同构的图等于没画**——类型不匹配，
  读者得自己在脑子里转换。
- **点出接口**——责任交接的那个确切 API（别叫它"接缝"，见 references）。
  接口是读者真正在找的东西；点出它，读者就能自己把整条路推出来。
- **形态变化要落到代码结构**。凡是数据"形状变了"的一跳，都要给出真实的
  类/结构体定义（逐字抄 + `file:line`）。**尤其是 KV block**：从调度器的逻辑块号
  到网卡认得的地址，中间至少四次表示，每一次都要给结构。
  散文里的"一段 KV"糊得过去，`struct KVBlockDesc { uint64_t addr; ... }` 糊不过去。
- **每个参与仓库都要钉版本**，它们各自漂移。

展开见 `references/plugin-and-cross.md`。

## 8. 校验清单

### 先跑脚本，再逐条自查

> **还有一条不在这个校验器里**：文风体检（§5.5）。它需要项目自己有一个
> 「数 AI 腔 + 锚点总数只许增不许减」的脚本，并接进 CI——
> 否则去 AI 腔会退化成删句子。

**文字铁律容易忘，所以有一支可执行的校验器**：

```bash
# 单个模块
node scripts/check_module.js data/analyses.js lmcache engine

# 全部模块
node scripts/check_module.js data/analyses.js lmcache --all

# 总分结构：总体设计图里的方框 ↔ 关键模块（§3.9.2 的铁律）
node scripts/check_module.js data/analyses.js lmcache --design

# 宿主不写插件：拿插件声明的别名扫宿主页（§3.0.00 的铁律）
node scripts/check_module.js data/analyses.js --cross

# 加 --repo 做两件事：
#   ① 核对每个 file:line 是否落在有效行范围内，并回显那一行
#   ② 核对正文里引用的每一行代码在仓库里是否真的存在
#   ③ 核对文中出现的每个文件路径是否存在、是否会被同名文件模糊
#   ④ 核对每个站内链接 #/... 是否指向真实存在的页面
#   ⑤ 核对 > 引用块里的 docstring 摘录是否逐字（按子句 + 词边界比对）
node scripts/check_module.js data/analyses.js lmcache engine \
  --repo /path/to/source-repo
```

**它检查的是能自动判定的那部分**：节顺序、公开 API 是否混入内部件、
「关键流程」有几条路径对「关键实现」有几张图、结构体定义是否为真实代码、
关键文件是否分档、全文有没有 `file:line`、
**总体设计图里的每个方框有没有模块**（`--design`）、
**宿主页有没有写插件**（`--cross`）。

**扫的是整页文字**，不只是正文小节——
模块级 `lead`、分析级 `summary` / `scope` / `notCovered`、
表格与 `chain` 里的字，**都在扫描范围内**。
（这一条是补出来的：原先只扫 `section.html` 与 `blocks[].html`，
于是 `%%TokensHash%%` 藏在一个模块的 `lead` 里躲过了标识符核对，
两处"宿主写插件"也躲在 `summary` / `scope` 里。）

**它查不出的**（必须自己看）：图与文是否对得上、
解读是否只是复述图、断言是否真的读过代码、
**同一个事实在多处各说一遍时是否已经改齐**、
**"没点名但整段在讲别处"的越界**（见 §3.0.00）。

#### 术语：本页用的每个词，都要能搜到

**§3.0.0 的术语纪律说白了就一句**：
**读者复制这个词到代码里搜，必须搜得到。**

**本项目真实错误**（藏了 26 轮才被发现）：
用 **"不做 lookaside（旁路查他人缓存）"** 去概括 `post_init` 那六个条件之一。
**`lookaside` 这个词在整个仓库里出现 0 次**——是我造的。

**改成代码里的名字就对了**：
「**没有 `%%lmcache_worker%%`（不接控制面）**……」——`lmcache_worker` 搜得到，
读者一眼知道说的是哪个条件。

**判据**：**把页面里所有 `%%...%%` 之外的名词性短语列出来，逐个搜一遍。**
搜不到的分两种：
- **是代码里的东西** → 换成真实标识符
- **是你在描述行为**（"透传通道""编排者"）→ **可以留，但紧接着要有一句解释**

**为什么这类错误特别难自己发现**：**自造词读起来最顺**——
它比 `lookaside` 换成"该 rank 没有 worker"更像一句行话。
**顺口不等于有据。**

#### 定稿前扫一遍"绝对化措辞"

**「唯一」「全部」「所有」「只有一处」「从不」这类词，是最容易写错的一类断言**——
**它们不是观点，是可证伪的事实，而证伪成本很低。**

**本项目真实错误**：同一页里两处打架——

| 位置 | 写法 |
|---|---|
| 「关键数据结构」 | `%%storage_manager%%` 是**唯一一个自己 new 的协作者** |
| 「用途与职责」 | **自己 new**：`%%lmcache_worker%%` / `%%event_manager%%` / `%%hidden_state_store%%`（**三个**） |

**加在一起是四个，"唯一"是错的。** 正确说法是"**唯一一个在 `%%post_init%%` 里创建的**"
（另外三个在 `%%__init__%%` 里）。

**同一轮还抓到**：「Builder 要把**所有依赖**装配好」——
但 `%%storage_manager%%` 是 Engine 自己在 `%%post_init%%` 里造的。**"所有"也是错的。**

**定稿前逐个确认**：搜「唯一 / 全部 / 所有 / 只有 / 从不 / 一律」，
**每一处都问自己"要反驳它，我需要找出几个反例？找一个试试。"**

**这类错误校验器查不出**（它不知道"唯一"的论域是什么），
**但比"读图是否复述"好查得多——因为它是二值的事实判断。**

#### 同一个事实说了几遍，就要改几遍

**这是最阴的一类错，因为它不会自己暴露。**
本项目真实案例：`MemoryAllocator` 不是运行期依赖——
**这个结论我在三个小节里各写过一次，改的时候只改了「依赖」那一处。**

| 位置 | 当时还留着的旧说法 |
|---|---|
| 「用途与职责」的**下游**行 | 列着 `memory_allocator` |
| 「依赖」节 | 「上游依赖 \| MemoryAllocator」← **只改了这里** |
| 「内部结构」的说明段 | 「所以有 `_Create_token_database` / `_Create_memory_allocator`」 |

**读者翻到任何一处都会读到旧结论，而四处校验全绿。**

**做法**：**同一个事实只在一处展开，其余地方只留一句指引**
（"见「关键实现 ④」"），**根本不给它漂移的机会**。

**确实需要多处提及时**（比如 layerwise 的摘要出现在「公开 API」「关键流程」「关键实现」），
**定稿前搜一遍关键词，把每一处都过一眼**。

**校验器会把这类位置列出来**（不需要 `--repo`，只看正文）：

```bash
node scripts/check_module.js data/analyses.js lmcache engine
#   跨节重复的事实 1 条（改一处记得改其余）：
#      cache_engine.py:485    出现在：flow、impl
```

**它数的是"同一个 `file:line` 出现在几节里"**——
**出现在两节以上就是风险点，去确认两处的说法一致。**

**它会核对「公开方法有没有被提到」**——**从模块的 `主要文件` 里找出方法最多的那个类，
逐个检查它的公开方法在本页出现过没有；有外部调用方却没提的，就是缺口**：

```
方法未覆盖（LMCacheEngine 里这些公开方法有调用方，但页面没提）：
  get_kv_events
```

**本项目真实漏过两个**：`%%clear%%` 与 `%%get_kv_events%%`——
**后者被 sglang 与 vllm 两个适配器调用**，是确凿的对外接口，
**而「公开 API」那一节里没有它**。

**为什么容易漏**：写「公开 API」时习惯按"我知道的那几条主干"列，
**而不是按"代码里到底有哪几个公开方法"过一遍**。
**这个检查强制你过一遍。**

（注：它按"方法最多的类"认主类，**可能挑中辅助类**——
命中的先人工确认一下再改。）

**它还会核对 `%%...%%` 里的标识符能不能在仓库里搜到**：

```
标识符存疑（1 处，仓库里搜不到）：StorageMgr
```

**只查三类够具体的**（CamelCase 类名 / `_私有名` / `xxx()`），
**通用词（`True` / `key` / `mask`）和概念词（`chunk`）不查**——否则全是噪声。

**本项目实测**：20 个模块里有 **7 个**报了，抽验全是真问题——

| 写的 | 代码里真实的 |
|---|---|
| `_input_queue` | **`_ops_queue`** |
| `ServerTransfer` · `TransferMetadata` · `Compressor` · `DevDaxL1Config` | 都不存在 |

**它会核对 `%%` 是否成对**——**一个单 `%` 会让后面的配对全乱，页面上直接漏出字面量**：

```
错误：%% 标记没成对（页面会漏出字面量 %%）：position（85 个，奇数）
```

**本项目真实犯过**：把 `%%metadata.worker_id%%` 打成了 `%metadata.worker_id%%`——
**开头少一个 `%`**，于是整节的行内代码标记全部错位。

**它还会核对围栏的语言标记**——

```
提示：有 2 个代码围栏没写语言标记（裸 ~~~）——它们不会被逐字校验：interface、impl
```

**这不是格式问题，是校验失效**：裸 `~~~` 会被当成"作者自己的记号"跳过，
**等于你自己放行了引用错误。** 本项目 20 个模块里有 4 个中招。

**它还会核对 lead 里的条数**——**加了新块却忘了改 lead 的数字**，
也是"改一处忘改其余"：

```
提示：lead 里的条数与实际不符：impl 的 lead 说「三条」，实际有 4 块
```

**同一份报告里还有一项"页内重复的行"**——
**把同一句话写两遍，读者会以为你在强调，其实只是复制粘贴。**

本项目实测：`mp-modules` 一页里有 **8 处**重复的正文行。

**判据**：**同一句出现在两处，删掉一处，剩下的那处还读得通吗？**
读得通就删——**重复不产生信息，只产生"这里是不是有区别"的疑问。**

（围栏里的源码不算——同一行代码出现在两个片段里是正常的。）

## 9. 反模式

| 反模式 | 为什么失败 |
|---|---|
| 细节先于结构 | 读起来像逐行转述，读者无处安放任何东西 |
| 自动生成的"架构图" | 画的是解析器视角，不是设计；一团毛线 |
| 把所有类都画进类图 | 同样的失败；没有信号 |
| 不标注的箭头 | 关系本身就是信息 |
| 按目录罗列（"`foo/` 下有…"） | 有结构没有含义；读者自己会 `ls` |
| **自造模块名**（如「跨实例取数」） | 读者在代码里搜不到；应直接用 `P2PBackend` 这样的真实标识符 |
| **罗列易变清单**（逐条补丁表、逐行配置） | 代码一改就腐烂。写**类别与机制**，举少量例子 |
| 从"合理性"编造动机 | 自信地错，而且读者无法证伪 |
| 不钉版本 | 仓库一动文档就过期，且无法察觉 |
| 跳过质量属性 | 丢掉的恰好是需要经验才能写的那部分 |
| **程式化的破折号**（`结论——解释` 用成模板） | de-slopify 与 Wikipedia 都列为文档类第一号 AI 标志；读者一旦认出，你锚的每一行都被一起打折 |
| **用脚本批量改措辞** | 替换不是重写。本项目实测：批量换「这也解释了为什么」造出了「所以"为什么两条线都存在"」这种自相矛盾的句子 |

## 10. 页面内容改动的固定动作

§1–§9 讲的是"怎么写一页"。这一节讲**"改一页"**——它们出错的概率高得多，
因为改动往往只碰一个字段，而**这个字段可能被别处以别的方式依赖**。

以下每条都来自真实事故，不是假想。

### 10.1 改模块名要同步四处

改 `title` **只是第一步**。同一处名字还出现在：

| # | 位置 | 检查方式 |
|---|---|---|
| 1 | 组名尾巴（`group`） | 组名里若引用了模块名，一起改 |
| 2 | 跨页链接文字 `[老名](#/a/<id>/<mid>)` | **全库 grep 老名** |
| 3 | 图里的 `aria-label` | grep 老名 |
| 4 | 正文引用 | grep 老名 |

**收尾动作固定为**：`grep 老名` 到 **0 次**。

**事故**：一个模块改了三次名（`宿主适配器` → `LMCacheMPWorkerAdapter` → `Integration`），
每次都只改了 `title`，`宿主适配器` 在数据里残留 **16 处**（含 12 处跨页链接）。
**没有一条校验规则能抓到它**——链接文字与正文都是自由文本。

### 10.2 整体替换模块对象会丢字段

用 `new={id,title,...,sections}` 整体替换旧模块时，
**旧模块上不在 `new` 里的字段会静默消失**。

**最容易被丢的是那些"后加的、非骨架的"字段**：
`designSymbols` · `designExternal` · `designUncovered` · `modulesLead` · `notCovered`。

**事故**：重排 lmcache-ascend 六个模块后，它们的 `designSymbols` 全没了，
`--design` 从 0 错变 8 错——**而单模块校验全是 ✅**。

**规则**：**替换后立刻跑 `--design`**，它专门查这类"认领丢失"。

### 10.3 按行去重必须排除围栏

"删掉页内重复的行"这个动作**不能按行文本无差别执行**——
**代码围栏里的行也可能重复，而它们必须留着**。

**事故**：一次去重删掉了代码围栏里的若干行，该模块错误数**从 41 升到 42**。

**规则**：去重前先切分"围栏内 / 围栏外"，**只对围栏外的行去重**。

### 10.4 围栏内不许出现 markdown

`**加粗**` · `%%标识符%%` · `| 表格 |` 在代码围栏里**不会渲染**，
会**原样显示成星号、百分号、竖线**。

**事故**：三处不同模块的 python 围栏里分别混进了 `**默认值**`、`%%on_keys_touched%%`、markdown 表格。

**规则**：写围栏时只想一件事——**"这一行会被逐字比对"**。
要放示意或说明，用 `~~~text`；要放注释，用 `#`。

### 10.5 `~~~text` 是"这不是源码"的标记

校验器**只逐字比对带语言标记的围栏**，`~~~text` 属于跳过之列。

**两类内容应该用它**：

| 内容 | 例子 |
|---|---|
| ASCII 示意图 | `▼ 按 chunk_size 切` / `h0  h1  h2` |
| 示意或反例 | `# ❌ 看起来自然，但错` 那种对照代码 |

**不这么做的代价**：约 **200 行**示意图被误报成"片段存疑"，
而它们**本来就不可能也不该在仓库里找到**。

### 10.6 转述的代码必须重引

**代码围栏必须是仓库原文。** 常见走样形式：

| 走样 | 例 |
|---|---|
| 多行签名压成一行 | `def f(a, b, c) -> T:` ← 真实是四行展开 |
| 丢掉类型标注 | `def f(model_name, world_size)` ← 真实带 `: str, : int` |
| 丢掉 `self` | 同上 |
| 改写 docstring | 把 `:class:` 标记去掉、把换行重排 |
| **编造标识符** | `_construct_subkey` ← 真实是 `_make_key_by_hash` |
| **大小写写错** | `ServerTransfer` ← 真实是 `server_transfer` |

**前三种靠眼睛看不出来**——它们"看起来就是真代码"。

**工具**：仓库根放一个 `requote.py`，按
`(模块id, 围栏内锚点, repo文件, 起止行)` 用原文替换围栏：

```python
import sys; sys.path.insert(0, '.')
import requote
requote.run([('mp-transport', 'class RequestClient(Protocol):',
              'lmcache/v1/multiprocess/transport/base.py', 11, 23)])
```

**它必须先试解析再写入**——锚点若落在正文而非围栏，切片会拼出非法 JSON。
（这一点也是踩出来的：早期版本会带着破损内容继续跑。）

### 10.7 裸文件名一律加目录限定

只写 `factory.py:29` 会被判**歧义**——仓库里可能有 7 个同名文件。
**必须写清相对路径**。

另外三类容易漏的：

| 情况 | 处理 |
|---|---|
| 扩展名不在校验器表里（`.js` `.md` `.pyi` `.sh` `.png`） | **移出 `%%`**，或写成目录加尾斜杠 |
| 斜杠 token（`send/recv`、`protocols/p2p`） | **会被当成路径**——拆成两个 `%%` |
| `__init__.py`（可能有 159 个同名） | 写成「`<目录>/` 的 `__init__.py`」 |

### 10.8 写 markdown 前先确认那处会渲染 markdown

**同一份数据里，不同字段的渲染方式不同**：

| 会渲染 markdown | 原样输出 |
|---|---|
| `lead` · 各节 `html` · `notCovered` · `summary` · `scope` | `title` · `subtitle` · `files` · `h3` · 组名 · **SVG 里的文字** |

**事故**：`modulesLead` 走的是原样输出，于是 `**加粗**` 显示成了字面星号。

**规则**：**往一个字段里写 markdown 之前，先确认那个字段过不过渲染函数**。
`lint_svg.py` 的 `check_raw_fields` 能查出字段级的漏网，但**查不出"某个输出位置忘了调渲染器"**——
那一类只能靠看。

### 10.9 收尾固定跑一遍

内容改完后，**同一轮内**依次跑：

```bash
python3 fix_fences.py     # 围栏标记与反引号
python3 lint_svg.py       # SVG 与字段里的 markdown
node scripts/check_module.js data/analyses.js <分析> <模块> --repo <repo>
node scripts/check_module.js data/analyses.js <分析> --design       # 认领没丢
node scripts/check_module.js data/analyses.js --cross               # 宿主没写插件
```

**再渲染看一眼**——`--dump-dom` 后检查 `<h1>`、`<h2>` 数、`class="diagram"` 数，
以及**有没有字面 `**` / `%%` / `~~~`**。

**注意 `**` 的误报**：页面里合法的 `**kwargs` 也会命中，需要看上下文。

### 10.10 空围栏会带偏后面所有内容

`~~~python` 紧接 `~~~`（中间没有内容）时，围栏的**配对会错位**——
校验器会把**后面的正文当成代码**逐字比对。

**症状很隐蔽**：错误数**暴涨**，而报出的"找不到的代码行"
**其实是紧跟其后的 markdown 表格与散文**（`| 分层 | 结构 |`、`最近性是它在 OrderedDict 里的位置`）。

**事故**：全库 3 个空围栏，共造成 **19 个假错误**。
删掉后 lmcache 从 153 错降到 134，某一页单页从 24 降到 6。

**规则**：

- **不要留空围栏**——要贴代码就贴，没有代码就删掉标记
- 若错误里出现"**散文或表格行被当成找不到的代码**"，
  **第一反应是往上找有没有空围栏或未闭合的围栏**
- 顺手扫一遍：`grep -c '~~~[a-z]*\\n~~~' data/analyses.js`

### 10.11 去掉重复的行号引用会换来一个歧义

"跨节重复"这条提示的修法是：**同一条 `file:line` 只保留在最相关的一节**，
其余节里把它降级为不带行号的形式。

**但降级成裸文件名会立刻触发"路径有歧义"**——
`%%server.py:291%%` 去掉行号后是 `%%server.py%%`，而仓库里有 3 个同名文件。

**所以降级时要一并补上目录**：`%%lmcache/v1/multiprocess/server.py%%`。

**事故**：一次去重 22 处，错误数先 130 → 131（多出一个歧义），
补全目录后 131 → 128。**净收益来自"补目录"，不是来自"删行号"。**

**规则**：**凡是把 `path.py:NN` 改成 `path.py` 的地方，同一步就写成完整相对路径。**

### 10.12 引文可以来自设计文档，但代码片段不行

校验器原本**只加载源码扩展名**（`.py` `.cpp` `.h` …），
于是**任何从 `docs/design/**` 摘来的 `>` 引文都会被判"仓库里找不到"**。

**事故**：9 处误报里有 7 处属于这一类——
例如 l2-adapters 那句 *"All event fds across all adapters must be globally unique"*，
**它确实存在，在 `docs/design/v1/distributed/l2_adapters/overall.md` 里**。

**修法有分寸**：

| 检查 | 语料 |
|---|---|
| **引文**（`>` 摘录） | **源码 + `docs/**` 文档**——设计文档本就是可引用的出处 |
| **代码片段**（围栏） | **只用源码**——否则抄错的片段可能恰好命中文档里的示例而蒙混过关 |

**所以"把 `.md` 加进语料"这件事不能一刀切**：
加给引文是修误报，加给片段是放松标准。

**写页面时的对应规则**：引用设计文档时**把出处写清**（`docs/design/...`），
不要让它看起来像源码摘录。

### 10.13 引文校验的"从句"规则与它的边界

`verifyQuotes` 的做法是：

1. 把连续的 `>` 行拼成一段（**少于 2 行或不足 24 字符的不查**）
2. 剥掉 `%%` `**` `*` `_` 与引号，并归一化 RST 标记（` ``X`` ` → `X`、`:class:` 前缀）
3. **按 `, ; . 。 ， ；` 切成子句**，**每段 ≥4 个词**的子句都必须能在仓库里找到

**它能查出**：中段改字（不是只看最长前缀）、少抄一个词。

**它查不出的两类**（都会误报）：

| 情形 | 说明 |
|---|---|
| **子句跨原文换行 + 带 RST 标记** | 实测中同一段引文的 4 个子句有 3 个逐字命中，第 1 个失败——**引文其实忠实，是归一化没吃干净** |
| **来自 `docs/**` 的引文** | 见 §10.12（已修：引文语料现在含文档） |

**写页面时的稳妥做法**：

- **引文尽量短**——一段一句，别把整段 docstring 抄进来
- 需要跨句时，**宁可拆成两段 `>` 引文**，也别在一段里用 `...` 省略（省略号会把子句切开，反而更难对）
- 如果一条引文**反复报错而核对后确认真实**，**在页面里注明出处**（文件 + 那一段的作用），
  **不要为了通过校验而改写原文**——引文逐字这条纪律比一条绿勾重要

### 10.14 去 markdown 标记时不要连下划线一起去

引文比对前要剥掉 markdown 强调标记。**但 `.replace(/[*_]/g, '')` 是错的**——
`_` 是**标识符的一部分**：

| 原文 | 剥掉 `_` 之后 |
|---|---|
| `csrc/engine_kv_format.h` | `csrc/enginekvformat.h` |
| `get_spec_class` | `getspecclass` |

**这两个都不可能再匹配**，于是"引文存疑"。

**事故**：这一条造成 **7 个假引文错误**（lmcache 从 123 降到 116）。
加上空围栏（19 个）与文档引文（7 个），**本轮工作里累计有 33 个错误根本不存在**。

**正确做法**：只去 `**` 与 `*`，**保留 `_`**。

```js
.replace(/%%/g, '').replace(/\*\*/g, '').replace(/\*/g, '')   // 不要带 _
```

**排查这类问题的思路**（这一条比结论更有用）：

> 看到一个"引文存疑"反复核对后确认**原文忠实**时，
> **不要继续核对引文**——去核对**校验器比对前做了什么清洗**。
> 把清洗逻辑单独跑一遍，打印**它实际拿去比对的那几段文本**，
> 差异几乎总是立刻显形（本例里打印出来是 `enginekvformat` 和 `getspecclass`，
> 下划线不见了，一眼就能看出是被谁吃掉的）。

**同理适用于**：`~~~text` 的跳过规则、引文语料的文件扩展名、空围栏的配对。
**它们都是"比对前的一步"，而错误往往出现在那里，不在内容里。**

### 10.15 剥 markdown 不能碰代码围栏里的 `**`

§10.4 说"围栏里不许有 markdown"——但**执行这条时不能用"全局替换 `**`"**。

**因为 Python 的 `**kwargs` 就是两个星号。**

**事故**：一次"全库清理围栏内 markdown"，把 **6 个模块**里的
`**kwargs` 改成了 `kwargs`——

| 页面被改成 | 仓库里是 |
|---|---|
| `def to_gpu(self, memory_objs, start, end, kwargs)` | `... end, **kwargs)` |
| `def submit(..., affinity_key: int = 0, kwargs)` | `... **kwargs)` |
| `self.gpu_connector.batched_from_gpu(memory_objs, starts, ends, kwargs)` | `... **kwargs)` |

**这是"修渲染问题反而改坏了真代码"**——比原来的问题严重，因为原问题是显示层、这个是内容层。

**正确做法**：

- **按"位置"清理**，不要按"符号"清理：只处理**已知会误渲染的模式**
  （行首的 `**标题**`、包住标识符的 `%%...%%`）
- **或先在围栏外清理，围栏内只做白名单替换**
- **清理后必须跑一次 `--repo` 校验**——这类破坏只有它能发现
  （`kwargs` 与 `**kwargs` 在肉眼看来都"像代码"）

**普遍教训**：**对全库做无差别文本替换前，先问"这个模式在代码里有合法用法吗"。**
`**`（`**kwargs`）、`_`（标识符，见 §10.14）、`#`（字符串里的井号）都属此类。

### 10.16 把围栏标成 `~~~text` 会**隐藏**真实错误

§10.5 说示意图该用 `~~~text`——**但这是个"跳过校验"的开关，用错方向就变成藏错**。

**事故**：一次批量把"疑似示意图"改成 `~~~text` 时，
**误伤了 `eviction-policy` 里一个 21 行的真实方法**（`lru.py:128` 的 `get_eviction_actions`）。
它从此不再被逐字比对——**页面里那 21 行对不对，没人知道了。**

**规则**：

- **改 `~~~text` 前先看内容**：有 `def` / `class` / `import` / 类型标注的，**一律是真代码**
- 判据不是"看起来像图"，而是**"这能不能在仓库里找到"**——
  能找到的一律留 `python`
- **批量 retag 之后要复查**：扫一遍所有 `~~~text`，
  凡是含 `def ` / `class ` / `import ` 的，逐个确认

**这条与 §10.15 是同一个道理的两面**：
**批量操作会同时造成"改坏内容"（10.15）与"藏起内容"（10.16）**，
而两者都不会立刻显形——**只有 `--repo` 校验能发现前者，后者连它也发现不了**
（因为它已经不校验了）。

**所以：任何让检查"变宽松"的批量操作，都要单独复核一遍。**

### 10.17 补上裸围栏的标记，错误数会**上升**——这是对的

裸围栏（`~~~` 不带语言）**不参与逐字校验**。
给它们补上 `~~~python` 之后，**原先被藏住的错行会立刻暴露**。

**事故**：给 serde 的 2 个裸围栏补标记后，
该模块错误数 **6 → 13**——**多出来的 7 个全是原本就存在的问题**。

**所以看到"补标记后错误变多"不要慌、也不要回退**：

| 动作 | 计数 | 真相 |
|---|---|---|
| 保持裸围栏 | 6 | **假的**——11 行从未被核对 |
| 补上标记 | 13 | **真的**——11 行暴露出来，等修 |

**这与 §10.16 是同一枚硬币的两面**：
放宽检查会**藏**错（10.16），收紧检查会**显**错（10.17）。
**两个方向都要能识别**，否则会在"数字好看"与"数字难看"之间做错误的选择。

**判据**：**只要改动方向是"让检查更严"，计数上升就是正常且值得的**——
**唯一要确认的是"上升的项确实是真实欠账"，而不是新的误报。**
（对照 10.10–10.14：那几次是让检查更准，计数下降。）

### 10.18 批量加标记时，正则不要同时命中开与闭

`re.sub(/~~~\n/, '~~~python\n', html)` 看着只匹配"裸的开围栏"——
**但闭合的 `~~~` 后面通常也有换行**，于是**闭合位也被加上 `python`**。

**事故**：一次这样的替换让 serde 的围栏配对全乱，错误数从 6 涨到 13
（其中一部分是配对错乱、一部分是 10.17 说的"翻出旧账"）。

**正确做法**：**用"交替"来定位，不要用正则**——
围栏标记必然是**开 / 闭 / 开 / 闭**交替出现的：

```python
marks = list(re.finditer(r'~~~[a-z]*', html))
for i, m in enumerate(marks):
    if i % 2 == 1:        # 闭合位：必须是裸的
        ...
    else:                 # 开启位：可以带语言
        ...
```

**这条对 §10.15 也适用**：任何"只改某一种标记"的批量操作，
**先确认这个标记不会在另一种位置出现**（`**` 出现在 `**kwargs`、`_` 出现在标识符、
`~~~` 出现在闭合位）。

### 10.19 §10.3 的修订：去重的判据不是"这行重复"，而是"删了结构还成立吗"

§10.3 说"按行去重必须排除围栏"。**实测证明这条不够**——
**段落里的行也会重复**（两节都提到同一句话），而删掉它会留下：

| 留下的残骸 | 例 |
|---|---|
| **断头表格** | `|---|---|---|` 后面直接跟数据行，**表头行被删了** |
| **空段落** | 标题下面连着几个空行，正文不见了 |
| **半截围栏** | 围栏里只剩 docstring 的中间几行 |

**事故**：`transfer-module` 的「关键实现」节被删成这样——
一个残缺的 docstring 片段、两个断头表格、几处空白。**整节只能重写。**

**修订后的规则**：

- **不要在"全文范围"去重**——重复出现在不同小节里往往是**有意的呼应**
- 真要处理"跨节重复"这条提示，**只动 `file:line` 这类机械引用**（见 §10.11），
  **不要动散文**
- **任何批量删行之后，必须逐节渲染看一眼**：
  **表格是否还有表头、标题下是否还有正文**——
  这些**校验器一条都查不出来**（它只看"有没有图、行号对不对"）

**扫描这类残骸的方法**（比读全文快）：

```bash
# 断头表格：分隔行前面不是表头行
grep -n '^|---' data/analyses.js | while read -r l; do ... done
# 更简单：找出"标题后连续两个空行"或"表格分隔行紧跟非表头"的位置
```

**结论**：**批量删内容的操作，风险与批量改标记同级**——
它不产生错误提示，只产生"看起来还在、其实已经断了"的页面。

### 10.20 大批量改写：内容与装配分离

重排一个模块往往要一次写进去五六个小节，
**而把这几千字塞进一个 Python heredoc 的三引号字符串里是最容易出错的做法**——
里面的引号、反引号、缩进、`%%` 都可能让脚本**语法错**（我为此失败过两次）。

**可靠的做法是分两步**：每个小节先写成一个独立的 `.txt`，再用一个**短脚本**读取并装配。

```bash
mkdir -p /tmp/<模块>/
cat > /tmp/<模块>/position.txt <<'TXTEOF'
...这一节的内容...
TXTEOF
# 其余小节各一个 txt
```

```python
rd = lambda f: open('/tmp/<模块>/'+f, encoding='utf-8').read().rstrip('\n')
S['position'] = {'id':'position','title':'用途与职责','html':rd('position.txt')}
# ... 其余小节
m['sections'] = [S[k] for k in order]      # 最后一次性按标准顺序输出
```

**好处**：

| | 塞进脚本 | 分文件 |
|---|---|---|
| 引号 / 反引号 | **要转义，易错** | **不用管** |
| 改一句话 | 改脚本、重跑 | **只改那个 txt** |
| 出错定位 | 看几百行脚本 | **看一个文件** |

**三个必须注意的点**（下面三条我都各犯过两次）：

1. **改完 `s['id']` 之后必须重建字典的键**——
   `S = {x['id']: x for x in S.values()}`，否则后面按键取会 `KeyError`
2. **不要用"遍历现有节"来驱动新节的插入**——新节在遍历时还不存在；
   **应当先收齐所有节，再按标准顺序一次性输出**
3. **写这类脚本时，heredoc 的分隔符不要用 `EOF`**——
   示例文本里很可能出现 `EOF` 这个词，**它会提前终止外层 heredoc**
   （这条规则本身就是在写它的时候踩出来的）

### 10.21 数据分两处存，检查也要看两处

页面内容可以放在 `section.html`，也可以放在 `section.blocks[].html`。
**校验器的若干检查只看了前者**，于是**用 `blocks` 组织的模块会被系统性误报**。

**已修掉的同类缺陷（8 处）**：

| 检查 | 漏看的地方 | 后果 |
|---|---|---|
「关键数据结构」缺代码围栏 | `data.blocks[].html` | 用 blocks 的模块全部误报 |
引文核对 | 模块页（只看组件页） | `TokensHash` / `cost_model` 的引文不查 |
引文语料 | `docs/**` | **7 个假错误** |
引文清洗 | 多剥了 `_` | **7 个假错误** |
代码片段核对 | 空围栏导致配对错位 | **19 个假错误** |
`designUncovered` | 不减去已认领的符号 | 页面与校验器说法不一 |

**写法上的规则**：**新增任何"扫页面内容"的检查时，
第一句就应当把三种来源都收齐**：

```js
const texts = [
  String(sec.html || ''),
  ...(sec.blocks || []).map(b => String(b.html || '')),
  ...(sec.blocks || []).map(b => String(b.lead || '')),
];
```

**排查时的规则**（与 §10.14 同一条思路）：

> 看到某个检查**大面积、成片地报同一类错**时，
> **不要逐个去改内容——先去看那个检查读了哪些地方。**
> **"成片"是检查逻辑有问题的特征；"零散"才是内容有问题。**

### 10.22 计数不变有两种含义，要分清

消掉一个错、又冒出一个新错时，**总数不变**——
**这时只看总数会误以为改动无效。**

**这一路出现过两次**：一次是"补围栏"消掉了缺围栏、却因为我写错 `%%` 而报出"标记没成对"；
另一次是"补裸围栏标记"翻出旧账（§10.17）。

**规则**：**改动后不要只比对总数，要比对"错误的类别构成"。**
`check_module.js` 的分类输出就是为这个用的——
**同类错减少、异类错新增，说明改对了但要接着修新的那一类。**

### 10.23 「检查太吵」时要一次查完同族问题

本轮一次查出 **5 个**同类检查缺陷（编号接 §10.21 的 8 处）：

| # | 缺陷 | 误报量 |
|---|---|---|
| 9 | C/C++ 的 `//` 注释没剥（只剥了 Python 的 `#`） | mooncake 两页 **−24** |
| 10 | 路径检查的"目录"分支吞掉了文件名，且漏了 `listing.includes(tok)` | 真实存在的 `.md` 被判"路径不存在" |
| 11 | 引文核对**归一化不对称**：页面侧剥了 `**`，语料侧没剥 | 引用带粗体的设计文档永远失败 |
| 12 | 只认仓库根相对路径，不认**组件内相对路径**（monorepo） | `src/transport/xxx` 全被否 |
| 13 | 花括号展开 `a/{b,c}.py` 被当成一个具体路径 | 每次报"路径不存在" |

**共同点：全是"检查不认识正当写法"，而不是"内容写错了"。**

**规则**：
> **修一个这类缺陷时，顺手把同族的地方一次查完**——
> 注释标记、路径形态、归一化、相对性、通配写法，这五类各查一遍。
> 一个一个修，等于每轮都被同一族问题咬一次。

### 10.24 归一化必须**对称**

第 11 条是个通用陷阱，值得单独记：

> **凡是对"两边文本做匹配"的检查，两边的清洗规则必须逐字一致。**
> 页面侧剥了 `*`/`**`/反引号，语料侧也必须剥同样的；
> 只剥一边，带格式的那一侧就永远匹配不上。

**排查手法**：拿一条已知正确的引用，把它的原文从仓库里抄出来跑一遍匹配。
**匹配失败但看起来明明一样——那一定是某一边多剥/少剥了字符。**

### 10.25 `%%x%%` 在页面里是「行内代码」，检查却把它当「路径/标识符」

页面里 `%%...%%` 用来标**任何**行内代码，于是 `try/except`、`send/recv`、
`devdax_*.py`、`{a,b}.py` 都会被路径检查捞出来。
**这些是"斜杠词组/通配写法"，不是路径。**

**规则**：路径检查至少要放过三种非路径形态——
**语言关键字对**（`try/except`）、**通配**（`*` `?` `[]`）、**花括号展开**（`{}`）。
加一个 `SLASH_WORDS` 白名单即可。**宁可少查，也不要让作者为了消警告而把正常写法改丑。**

### 10.26 开查之前，先确认检出目录是**完整的**

本轮踩到一个隐蔽的坑：`codex/lmcache-review` 的检出里**缺了 56 个已跟踪文件**
（`git status` 显示 ` D`，blob 其实都在对象库里）。

**后果**：
- 用 `fs.existsSync(工作区)` 优先的脚本（包括本工具的 `repoData`）会**静默回退**到 `git show`，
  所以 `check_module.js` 没事；
- 但任何**只读工作区**的自查脚本会把这些文件里的每一行都判成"仓库里找不到"——
  **一次误报几十行**，而且看起来像"页面抄错了"。
- 更糟的是**作者**：检出不全时人会凭记忆写代码引用——这正是本页
  `_ZMQ_SCHEMES = frozenset(...)` 被当成"编造"的原因，其实它在 HEAD 里逐字存在。

**开工前先跑这一句**：

```bash
for d in codex/*/; do
  printf '%-26s 缺失=%-4s HEAD=%s\n' "$d" \
    "$(git -C "$d" status --porcelain | grep -c '^ D')" \
    "$(git -C "$d" rev-parse --short HEAD)"
done
```

看到 `缺失` 非 0，就先 `git -C <repo> checkout HEAD -- $(git -C <repo> status --porcelain | grep '^ D' | sed 's/^ D //')`
把工作区补齐（**只是恢复文件，零内容改动**），再开始核对。

> **凡是"成片报同一类错"，先怀疑两件事：检查的逻辑，和检查的前提。**
> §10.21 说的是前者，这条说的是后者。

### 10.27 补图/补说明时，**生成出来的文字也要过铁律**

本轮给 16 个模块补「读图」段，其中一段写成了：

> 中间那格……并注明都与**插件侧的 NPUConnector** 逐一对位

**这一句在宿主页（lmcache）提到了插件（lmcache-ascend）**，
直接违反 §3.0.00「宿主页不得提到插件」——
而且**同一句话在 SVG 里也有一份**（图内文字），两处都要改。

**为什么会漏**：
补图/补说明是"往里加内容"，注意力在"这张图画了什么"，
**不在"这段话有没有越界"**。人写正文时会想起铁律，插进去的说明却当成了图的一部分。

**规则**：
> **任何新生成的正文/图内文字，落盘前都要过一遍铁律清单**——
> 宿主页不提插件、公开 API 不提内部件、模棱两可的话不说、引文必须逐字。
> **尤其是"图里的文字"**：`--cross` 之类的检查**未必扫 SVG**，
> 图内文字成了盲区（本轮就是先只改了正文，`--cross` 才归零）。

**操作上**：补完一批自动生成的文字后，**除了跑常规检查，一定要再跑 `--cross`**，
并且**单独 grep 一遍插件名/内部件名**（`NPUConnector`、`lmcache-ascend`…），
因为"成片的同类检查"覆盖不到图内文字。

### 10.28 检查器的「提示语」要和「判据」一致

`「关键文件」看不出优先级分档（应当写"先读什么、为什么"）` 这条，
**提示语说的是「先读」，判据正则里却只有 `优先|第一|第二|精读`**——
于是作者照着提示语写下 `### 先读什么、为什么`，**照样判不过**。

**规则**：
> **凡是提示语里出现了一个词，判据里就必须认这个词。**
> 提示语是给人看的规范，判据是机器的规范，**两者不一致时，作者按提示语改也过不了**——
> 这是最难查的一类缺陷，因为错误信息本身在误导人。

**排查手法**：把提示语当查询串，到判据正则里搜一遍。搜不到就是缺陷。

**同一条还漏了 `blocks`**：`files` 节的检查只读 `files.html`，
而同一份代码里 `data` 节的检查**已经**把 `blocks[].html` 收进来了（见 §10.21）。
**同一族缺陷会在同一个文件里以不同面目反复出现。**

### 10.29 重复的**标题**不等于重复的**内容**

跨小节出现同一个 `### 标题` 时，有两种完全不同的情况，**处置相反**：

| | 特征 | 处置 |
|---|---|---|
| **复制粘贴** | 两段**高度重叠**（本例公共前缀 231/349、351/443，即 66~79%） | 留更完整的一版，另一处改交叉引用 |
| **总分结构** | 同一标题下**内容不同**（本例公共前缀仅 15~67 字符） | **不动**——`interface` 讲契约、`impl` 讲机制，同题不同深度是**对的** |

**判据是重叠率，不是标题是否相同。**
只看「标题重复」就去合并，会把正常的「总—分」写法砍掉——
那正是本站要的写法（§铁律：总分结构）。

**做法**：算两段的公共前缀长度 / 各自长度。**低于三成的一律不动。**

### 10.30 用 `%%` 做行内代码时，**落盘后必须看渲染**

本站不用反引号，行内代码一律 `%%x%%`。这带来两种只有**渲染后**才看得见的坏味道：

- `%%%%`（两个标记挨着，中间没有分隔）→ 会渲染出一个空 `<code>` 并把后面的文字吞进去；
- 写成 `` `x` ``（反引号）→ **原样显示成字面反引号**，因为渲染器不认反引号。

**`%%` 的成对检查（数奇偶）查不出 `%%%%`**——它是成对的，只是多余。
**只有渲染后的 DOM 才暴露它**（表现为 `%%<code>…</code>` 或空 `<code>`）。

**规则**：**任何批量写入正文的操作之后，除了跑校验器，一定要 dump 一次渲染结果**，
grep 四个东西：**字面 `%%`、字面反引号、字面 `**`、字面 `~~~`**。

```bash
chrome --headless --dump-dom --virtual-time-budget=9000 "http://127.0.0.1:8899/#/a/<页>/<模块>" \
  | grep -o '%%\|`' | sort | uniq -c
```

**注意区分真假**：源码围栏里的 `**kwargs`、docstring 里的 RST 双反引号 ` ``x`` `，
**都是逐字原文，渲染出来就该带这些字符**——不要为了消掉 grep 结果去改它们。
