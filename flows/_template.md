# 这里写标题（列表页与详情页顶部都用它）

> 这份是模板，**不用改它**——复制成 `flows/你的文件名.md` 再写。
> 文件名就是网址里的 slug，用英文小写加连字符，例如 `kv-return-paths.md`。
> 想再按项目分组就把文件放进一层子目录（如 `flows/vllm-ascend/`），
> 目录名会额外作为标签显示在卡片上。

**front-matter 基本可以不写。** 列表页要的标题、作者、日期、摘要都由 CI
从这份 md 和 git 历史里读出来，写进清单；**它只读，不会改动你的文件**。

唯一建议自己写一行的是 `section`——列表页按它**分章节**：

```markdown
---
section: mooncake
---
```

| `section` | 这一段收什么 |
|---|---|
| `lmcache` | LMCache 与 LMCache-Ascend：设计、集成与卸载方案 |
| `mooncake` | Mooncake Store 与 Transfer Engine：调用路径、竞品与选型 |
| `sglang` | SGLang 侧的跨组件链路 |
| `vllm` | vLLM 与 vLLM-Ascend：KV 卸载、传输与调度 |
| `新模型` | 新模型的 KV 形态带来的改动（DeepSeek V4.1 等） |

权威清单在 `tools/build_flows.js` 的 `SECTIONS` 里（顺序即展示顺序）；写错会被拦下
并列出全部合法值。都不合适就在那里加一行。不写也能投，只是会落进最后的「未归类」
段，生成清单时会有提示。

## 这一节写什么

联动分析跟**一次操作**走，不像深度分析页那样跟一个仓库走。所以开头先把两件事说清楚：

1. **这条链路横跨哪几个项目**，各自负责哪一段；
2. **读者跟着哪条线索往下读**（一次 KV 的存与取？一条回落通路？一个新模型的 KV 形态变化？）。

接着按参与方分段展开，每段给 `路径:行号`。

## 标题、作者、摘要从哪来

| 卡片上显示的 | 不写 front-matter 的话从哪来 |
|---|---|
| 标题 | 正文第一个 `# 标题` |
| 作者 | git 里添加这个文件那次提交的作者 |
| 日期 | 同一次提交的日期 |
| 摘要 | 正文第一段（自动截到一句话） |
| 标签 | 不自动填 |

哪一项想自己定，就在文件开头写那一行**覆盖**掉它——不需要写全，也不用记格式：

```markdown
---
summary: 我自己写一句摘要，比自动截的那句更准。
---
```

| 字段 | 要求 |
|---|---|
| `title` | 随便写；会原样显示 |
| `author` | 随便写 |
| `date` | `YYYY-MM-DD`，写错了 PR 检查会拦下 |
| `summary` | 一句话 |
| `tags` | `[标签1, 标签2]` |

## 能用的写法

普通 markdown 都能用。几个约定：

- 行内代码用 `%%双百分号%%` 包起来（不是反引号），例如 `%%MooncakeConnector%%`——这是本站的惯例，
  渲染出来是等宽小字。**注意 `%%` 里不能再出现 `%` 字符**。
- 代码块要写语言标记，例如 ` ```python `；ASCII 图与目录树写 ` ```text `。
- 表格、引用、有序无序列表、外链都正常。
- **原始 HTML 会被转义成字面量**（`<br>`、`<details>` 会原样显示出来），别用。
- 数学公式用 LaTeX：行内 `\(S_t\)`、行间 `\[ ... \]`（见下）。

```python
# 代码块会被逐字保留
def example():
    return 1
```

### 公式

行内公式写在 `\(...\)` 里，行间公式用一对独占的 `\[` 与 `\]`：

```text
状态递推为
\[
S_t = \widetilde{S}_t
      + \beta_t k_t \left(v_t - k_t^\top \widetilde{S}_t\right)^\top
\]
其中 \(S_t\) 是当前状态。
```

页面用**自托管的 KaTeX** 排版（本站不依赖外部 CDN），按需加载：文章里没有公式就不会去取那几个文件。
两条注意：

- **公式不要写进代码块**——围栏里的 `\(..\)` 与 `\[..\]` 会按字面显示，那是示例代码的待遇。
- `\[` 与 `\]` 之间**可以换行**，续行以 `+`、`-`、`*` 开头也没问题（渲染器把整段当一个公式块，
  不会误判成列表）。但别漏掉 `\]`，否则后面整段都会被吞进公式里。

## 图

把 SVG 文件**和 md 放在同一个目录**，正文里用图片语法引用：

```markdown
![这张图画了什么](你的文件名.svg)
```

几个要点：

- SVG 会被**内联**进页面（不是当图片加载），所以站点的图能直接拿来用——
  `fill="var(--panel)"`、`class="t-mono"` 这些主题变量和样式都生效。
  想省事就复制一张 `diagrams/*.svg` 改。
- `xmlns="http://www.w3.org/2000/svg"` 建议带上（内联后不影响，但文件单独打开要靠它）。
- 位图（`.png` / `.jpg`）也支持，用 `<img>` 加载。
- **别用外部图床**——本站不依赖任何外部资源，图必须跟着仓库走。
- ` ```mermaid ` 代码块**会被渲染成图**（站内自托管了 mermaid，按需加载、配色跟站内一致）。
  流程图 / 时序图 / 状态机都能写。图渲染出来点一下可以放大看细节。
- 想验证图有没有画对：`bash tools/verify.sh` 会跑 `lint_svg.py`，把文字重叠的框挑出来。

## 引用代码位置

写 `路径:行号`（例如 `mooncake-store/src/client.cpp:88`）时，
请**真的去那一行看过**。这类锚点会被 `tools/check_flows.js` 核对，
行号对不上会在 PR 检查里报出来。

如果你是按**自己那套检出**写的行号（跟本站分析页钉的基线不同），在 front-matter
里声明一下，校验器就按你的版本来核，不会误报「越界」：

```markdown
---
anchors: sglang=7465e42b, vllm=435c96f9
---
```

声明了、且本站检出里**恰好有那个提交**，就按它核（这时越界是真错误）；
没有就退回工作区文件比，越界只算提示。不声明则会有一堆版本差异造成的假越界。

## 目录（可选但推荐）

长文建议开头给个目录。站内的标题锚点规则**与 GitHub 一致**，
所以 `[标题](#锚点)` 在网页和 GitHub 上都能点；改了标题记得回头改目录链接，
`check_flows.js` 会核对这件事。

## 写完之后

1. `node tools/build_flows.js --lint` —— 两秒，查 front-matter（写了的话）与图片、锚点
2. `bash tools/verify.sh` —— 全套（含站内链接）
3. 提 PR

清单由 CI 重建，你不用碰，md 也不会被改。
