# 这里写标题（列表页与详情页顶部都用它）

> 这份是模板，**不用改它**——复制成 `flows/你的文件名.md` 再写。
> 文件名就是网址里的 slug，用英文小写加连字符，例如 `kv-return-paths.md`。
> 想按项目分组就把文件放进一层子目录（如 `flows/mooncake/`），
> 目录名会作为标签显示在卡片上，标题与 slug 里不用再重复它。

`flows/` 下的 md **没有 front-matter 也能投**：合进 main 后由 CI 补上
title / author / date / summary，并重建列表页要读的清单。你只管写正文。

## 这一节写什么

联动分析跟**一次操作**走，不像深度分析页那样跟一个仓库走。所以开头先把两件事说清楚：

1. **这条链路横跨哪几个项目**，各自负责哪一段；
2. **读者跟着哪条线索往下读**（一次 KV 的存与取？一条回落通路？一个新模型的 KV 形态变化？）。

接着按参与方分段展开，每段给 `路径:行号`。

## 唯一需要你决定的一件事：`direction`

`direction` 是**二级分类**，列表页按它分段。这个推不出来（是内容判断），
所以要么在文件开头写一行，要么等 CI 先归到「待分类」、你再去改一个词：

```markdown
---
direction: KV 全链路
---
```

可选值（权威清单在 `tools/build_flows.js` 的 `DIRECTIONS` 里，写错会被拦下并列出全部）：

| `direction` | 这个方向在问什么 |
|---|---|
| `KV 全链路` | 一次 KV 的存与取，横跨哪几层、各段怎么接上 |
| `传输与硬件后端` | Transfer Engine 与昇腾 / 鲲鹏 / UB 这些硬件通路 |
| `KV 存储与池化` | 分布式 KV 池、多级缓存、对象存储 |
| `KV 量化` | 把 KV 压小：分层量化与它的代价 |
| `框架集成` | 把 A 接进 B：方案设计与取舍 |
| `性能与容量` | 时延、吞吐、容量怎么估 |
| `社区与生态` | PR 梳理、上游贡献、社区格局 |
| `整体走读` | 把一个项目从模块地图到热路径读一遍 |

都不合适？别硬塞——在 `tools/build_flows.js` 的 `DIRECTIONS` 里加一行，
顺序就是列表页的展示顺序（新方向建议插在能挨着的位置，别放最后）。

## 其余 front-matter 字段（都可不写）

写了就以你写的为准，没写的自动推导：

| 字段 | 不写的话从哪来 |
|---|---|
| `title` | 正文第一个 `# 标题` |
| `author` | git 里添加这个文件那次提交的作者 |
| `date` | 同一次提交的日期 |
| `summary` | 正文第一段（自动截到一句话） |
| `tags` | 不自动填；写成 `[标签1, 标签2]` |

想改摘要、或想把日期写成文档日期而不是提交日期，就把那一行加上覆盖掉。

## 能用的写法

普通 markdown 都能用。几个约定：

- 行内代码用 `%%双百分号%%` 包起来（不是反引号），例如 `%%MooncakeConnector%%`——这是本站的惯例，
  渲染出来是等宽小字。**注意 `%%` 里不能再出现 `%` 字符**。
- 代码块要写语言标记，例如 ` ```python `；ASCII 图与目录树写 ` ```text `。
- 表格、引用、有序无序列表、外链都正常。
- **原始 HTML 会被转义成字面量**（`<br>`、`<details>` 会原样显示出来），别用。

```python
# 代码块会被逐字保留
def example():
    return 1
```

## 图

把 SVG 文件**和 md 放在同一个目录**，正文里用图片语法引用：

```markdown
![这张图画了什么](你的文件名.svg)
```

几个要点：

- SVG 会被**内联**进页面（不是当图片加载），所以站点的图能直接拿来用——
  `fill="var(--panel)"`、`class="t-mono"` 这些主题变量和样式都生效。
  想省事就复制一张 `diagrams/*.svg` 改。
- `xmlns="http://www.w3.org/2000/svg"` 建议带上（内联后不影响，但文件单独打开要靠它）。
- 位图（`.png` / `.jpg`）也支持，用 `<img>` 加载。
- **别用外部图床**——本站不依赖任何外部资源，图必须跟着仓库走。
- 注意：` ```mermaid ` 代码块**不会**被渲染成图，只会原样显示源码。要么换成 SVG，要么就别用。
- 想验证图有没有画对：`bash tools/verify.sh` 会跑 `lint_svg.py`，把文字重叠的框挑出来。

## 引用代码位置

写 `路径:行号`（例如 `mooncake-store/src/client.cpp:88`）时，
请**真的去那一行看过**。这类锚点会被 `tools/check_flows.js` 核对，
行号对不上会在 PR 检查里报出来。

## 目录（可选但推荐）

长文建议开头给个目录。站内的标题锚点规则**与 GitHub 一致**，
所以 `[标题](#锚点)` 在网页和 GitHub 上都能点；改了标题记得回头改目录链接，
`check_flows.js` 会核对这件事。

## 写完之后

1. `node tools/build_flows.js --lint` —— 两秒，查 front-matter（写了的话）与图片、锚点
2. `bash tools/verify.sh` —— 全套（含站内链接）
3. 提 PR

其余交给 CI：front-matter 与清单都会自动补好，你不用碰。
