# 推理后端的 KV Cache 分层量化：架构设计与避坑指南（修订版）

> 场景：LLM 推理后端（PD 分离 / 跨节点 prefill / tensor-parallel 跨卡），对 KV Cache 做分层量化（per-layer / per-channel 在 c8 / c6 / c4 间选档），同时服务于「省显存」与「压传输」两个目标。
> 本文综合 7 篇相关工作（CacheGen、KVTuner、UltraQuant、FlowKV、HMA-Serve、ShadowServe、KVServe），并基于多轮查证做了**三次重大修正**。
>
> 文档日期：2026-08-01（修订版，对初版的耐受表/二次压缩/动态存储三处错误做了纠正）

---

## 〇、修订说明：初版的三个错误

初版（同日早些 push 的版本）在论证链上有三处过度陈述或事实性错误，经查证后在本修订版全部纠正。**读者请以本版为准，初版的相关段落已废弃。**

| # | 初版的说法 | 查证结果 | 修正 |
|---|-----------|---------|------|
| 1 | 「模型出厂自带 per-layer 精度耐受表，随权重发布」 | **不成立**。DeepSeek-V3 权重里发布的是权重反量化 scale（`weight_scale_inv`，机械元数据），不是"该层能扛几 bit"的耐受表。真正的敏感度表是**部署方离线校准**生成的，且**与 workload 绑定、不能 zero-shot 迁移**（TriAxialKV 原文）。 | §3 重写 |
| 2 | 「后端是"对 MLA 原生压缩的二次压缩器"，两层正交可叠加」 | **被证伪**。MLA latent 是低秩紧凑空间，再量化是"在已去冗余的硬骨头上叠加噪声"。vLLM 官方把 MLA 类模型（Kimi-K2.5）点名列为 FP8 KV "consistent degradation" 的例外，需 case-by-case 校准甚至改 kernel。 | §8 重写 |
| 3 | 「按系统状态动态压缩的 KV 可以存储、跨周期复用」 | **逻辑不成立**。动态决策基于"当时负载"，决策有保质期；跨周期复用 = 用过期的决策服务新状态；进 prefix cache 还会跨请求污染质量。 | 新增 §7 |

另外，初版引用的「vLLM 上 MLA/DeepSeek FP8 从 91% 掉到 13%」**张冠李戴**：该数据是 **FlashAttention-3 的 FP32 累积精度 bug**（已修复），测试模型（Llama/Qwen/gpt-oss）**无一用 MLA**。它不是 MLA 二次量化的证据。本版删除该误用。

## 一、核心心智模型：代价 × 预算 → 决策 → 执行

KV 分层量化由四层组成，后端拥有后三层：

| 层 | 职责 | 回答的问题 | 输入来源 | 性质 |
|----|------|-----------|----------|------|
| **代价层** | 压到 c_n 会多伤 | "这层压 c4 掉多少精度？" | KV 数据 + 模型结构 | 静态/半静态 |
| **预算层** | 必须压到多狠 | "这次最多能用多少字节？" | 显存/带宽/deadline/SLA | 运行时，纯系统 |
| **决策层** | 每层/每块选几 bit | "在预算下最小化总代价" | 代价 + 预算 | 求解器 |
| **执行层** | 量化/传输/反量化 | "怎么真正编解码、不干扰计算" | 协议 + kernel + 硬件 | 工程 |

---

## 二、代价层：如何拿到「压了多伤」

### 2.1 两条实现路径

**路径 A：校准出一张逐层敏感度表（KVTuner 路线）**
- 离线跑校准集，对每层尝试候选位宽，测输出偏差。
- 产出 layer_i → {c8: ε8, c6: ε6, c4: ε4} 的表。
- K 比 V 敏感，常做非对称（K 高 bit，V 低 bit）。

**路径 B：用鲁棒量化算法抹平层间差异（UltraQuant 路线）**
- Walsh-Hadamard rotation 摊平 outlier + codebook 量化 + K/V 非对称，让 c4 在所有层都扛得住。

### 2.2 ⚠️ 修正：敏感度表不是随权重发布的，是部署方自己校准的

**这是初版最大的事实性错误。** 查证结论：

- **DeepSeek-V3 随权重发布的量化元数据**是 `weight_scale_inv`（128×128 权重 block 的反量化 scale，FP8/e4m3）和 `quantization_config`。这是"怎么把已量化的权重还原"的**机械元数据**，不是"该层能扛几 bit"的**耐受策略**。两者是不同性质的东西。
- **真正的逐层敏感度表**（KVTuner、TriAxialKV 那种），是**部署方/服务方**跑校准集生成的。TriAxialKV 原文明确：
  > "The per-tag sensitivity table is **calibrated per workload and per model**, requiring a one-time offline pass... this means the method is **not zero-shot transferable** to entirely new workloads."
- **没有任何主流模型把"per-layer 压缩耐受度"作为权重的一部分发布。** 模型作者发布的是**能力**（MLA latent 维度、FP8 weight scale、native 低比特权重），不是**部署策略**（"这层该用几 bit"）。

**对后端的影响**：你不能指望"读模型自带的耐受表"——你得**自建并维护校准管线**，按 workload 分桶缓存敏感度表。这是代价层的真实工程负担。

### 2.3 代价信号的两个时间尺度（不要混用）

| 尺度 | 内容 | 算的时机 | 开销 |
|------|------|---------|------|
| **层间**（架构性） | "第 12 层整体比第 37 层耐压" | 离线一次 | 零运行时 |
| **token/head 级**（内容性） | "这层此刻这块 outlier 多不多" | 运行时，看当前数据 | 需轻量代理量 |

最常见的错误是在 forward 热路径上重算层间敏感度——那是架构属性，读表即可。

## 三、预算层：什么信号驱动决策

预算信号全部来自运行时系统状态：

- **显存**：VRAM headroom、evict-or-quantize 阈值。
- **带宽**：当前链路带宽 × deadline 时间窗、并发流抢占。
- **SLA**：TTFT / TPOT / JCT 目标。

⚠️ **重要修正（来自 FlowKV）**：压缩不是压预算的唯一手段。**负载感知调度**能在很多场景下完全消除 KV 传输需求（FlowKV 不做任何压缩，纯靠调度 + 传输 kernel 优化，把 KV 传输延迟降了 96%）。后端要先想清楚"这几字节到底该压掉、还是该靠调度避开"。

---

## 四、决策层：求解器（后端的核心智力资产）

形式上是一道约束优化（多选背包）：

$$
\min_{b_i \in \{c8, c6, c4\}} \sum_i \text{cost}_i(b_i) \quad \text{s.t.} \quad \sum_i \text{bytes}_i(b_i) \leq B
$$

三种实现策略，从简到繁：

1. **贪心**：每层算"降一档的边际代价/边际省字节"性价比，从最划算的降起。增量友好。
2. **拉格朗日**：引入 λ 二分搜，更接近最优。
3. **学习式（KVServe 路线）**：bit 分配→实际延迟是非线性映射（量化/反量化/kernel/batching 效应），用解析延迟模型 + bandit 在线学习，修正"离线规划与在线执行的 mismatch"。目前最完整的决策器实现，9.13× JCT 加速。

**设计原则**：起步用贪心跑通 pipeline；延迟映射变复杂时再上学习式。

## 五、执行层：协议、kernel、反量化的位置

### 5.1 协议先行（所有能力的地基）
KV block 的传输/存储 header 必须带：`quant_level ∈ {c8,c6,c4}` + `scale 位置` + `layout` + `group size`。没有统一协议，逐层格式各异会让 PagedAttention、prefix 复用全部失效。

### 5.2 延迟反量化（deferred dequantization，HMA-Serve）
直接传原始量化字节，到对端再按需反量化。既省带宽，又避免过早反量化。

### 5.3 ⚠️ 反量化的执行位置是个独立架构决策（ShadowServe）
在 GPU/CPU 上反量化会**抢 attention 的算力**，反而拖慢。ShadowServe 把解压整个 offload 到 SmartNIC。优先用 fused dequant-attention kernel。

### 5.4 c6 的硬件现实（早验证）
很多硬件/库没有原生 FP6/INT6 解包路径。如果对端没有高效 c6 kernel，"三档动态"实际只有 {c8, c4} 两档可用。

## 六、正交杠杆：别只靠压缩

| 杠杆 | 代表 | 何时用 |
|------|------|--------|
| 分层量化 | KVTuner/KVServe | 确实需要省显存/带宽时 |
| 负载调度 | FlowKV | 能靠重调度消除传输需求时（**优先于压缩**） |
| 传输 kernel 优化 | FlowKV | 内核调用次数、内存分配是瓶颈时 |
| 解压 offload | ShadowServe | 反量化干扰计算时 |
| 结构压缩（模型侧） | MLA/DSA | 已随权重，白拿 |

**决策顺序**：先调度能否避开（FlowKV）→ 不能避开再压缩 → 压缩时优化执行。

## 七、⚠️ 关键修正：动态压缩的产物是「易腐品」，不宜跨周期存储复用

**这是初版完全遗漏的一层，也是最深层的一处。** 它动摇的是"动态压缩可省显存"这个前提本身。

### 7.1 矛盾：动态决策 vs 存储复用，是互斥的

> "按当前系统状态（显存压力/带宽）压出来的 c4 KV，能不能存下来，等系统状态变了再用？"

**严格来说不能。** 因为"当时为什么选 c4"这个理由，到使用时刻已经失效了。三种情况：

- **情况 1：压缩时刻和使用时刻系统状态基本不变（短间隔）** → 可以存。决策的理由还在有效期。这是 KVServe/CacheGen 动态压缩的主要场景：决策有效期 ≈ 一个调度周期。
- **情况 2：状态反转（压时显存紧，用时显存松）** → **问题所在**。低峰压的 c4，高峰想要高精度也回不去了（信息已丢）。决策的合理性有保质期，跨过保质期就是"用错误的理由做的压缩"。
- **情况 3：跨请求复用（prefix cache 共享）** → 矛盾激化。A 请求按"显存紧"压成 c4 存进 prefix cache，B 请求显存松本来想要 c8，却只能拿到 c4。**A 的系统状态决策，污染了 B 的质量。**

### 7.2 结论：存储的全部意义是复用；动态产物不能可靠复用，则存储无意义

把这件事讲透：**存储是为了复用。如果动态压缩产物（a）不能跨周期复用（决策过期）、（b）不能进共享池（状态污染）、（c）复用还会扩大错误——那它存下来没有意义。** 动态压缩产物要存，就只能在"本请求内、短周期"复用，而那个场景的存储价值本来就很小。

### 7.3 由此逼出的架构：存储压缩 vs 传输压缩，彻底二分

顺着这个逻辑，后端的 KV 压缩应被劈成**两套几乎无关的子系统**：

| | 存储压缩子系统 | 传输压缩子系统 |
|---|---------------|---------------|
| **用途** | KV cache 驻留 / prefix 复用 | 跨设备 KV 迁移 |
| **决策依据** | **模型属性**（离线敏感度表、MLA 结构）。不基于系统状态 | **系统状态**（当前带宽、deadline、对端状态） |
| **生命周期** | 长期，可进 prefix cache、可跨请求共享 | 极短，传输完即弃，对端反量化成存储格式 |
| **精度策略** | 保守（c8 为主），保住复用质量底线 | 可激进（链路差时压 c4，因只是一跳、马上解掉） |
| **复用安全** | 决策理由（模型属性）不过期，存任意久都合理 | 传输压缩的误差是一次性的，不累积、不驻留 |

**两套子系统共享物理 KV 数据和 kernel，但决策逻辑、生命周期、精度策略完全分离。** 揉在一起（初版就是揉在一起了）就会产生上述矛盾。

### 7.4 那"省显存"怎么办？

一旦接受"动态压缩产物不宜存储"，省显存的重任就从"动态量化"转移到了：
1. **静态量化**（离线算好每层 bit，整个服务周期固定）——这才是存储压缩的真身。
2. **模型原生结构压缩**（MLA latent）——省显存主力，随权重。
3. **Eviction / offload**（LRU 换出、卸到 CPU/NVMe）——不压，只搬。
4. **调度层省**（复用、batching、prefix 共享）——减少"需要驻留的 KV 总量"。

## 八、⚠️ 关键修正：后端与原生压缩是「执行 + 兜底」，不是「二次压缩器叠加」

### 8.1 初版的错误主张（已废弃）

初版说：「后端角色从主压缩器变成弹性层 + **对原生压缩的二次压缩器**，两层正交可叠加。」**这个主张被证据证伪。**

### 8.2 为什么"二次压缩 MLA latent"是危险且不值得的

MLA 把 KV 压进一个低秩 latent 空间，这个空间的特点是：
- **维度间强耦合**——每个维度的几何意义是训练学出来的。
- **冗余已被第一层吃掉**——剩下的都是"硬骨头"。
- **权重是按"latent 表示精确"训练的**——它没见过 latent 再被量化扰动的输入。

在这样一个空间上再叠数值量化（c8/c6/c4），误差会被 attention 的非线性放大。**这是"错上加错"**——对存储和传输都是最致命的精度风险来源。

### 8.3 证据：MLA 类模型被 vLLM 官方点名为例外

vLLM 的 FP8 KV 博客（2026-04-22）原文，在修复 FA3 累积精度 bug 后，把 MLA 类模型单独拎出来：

> "Some models (e.g., **Kimi-K2.5 with FlashMLA**) show **consistent degradation** with uncalibrated FP8."

判断标准是：**"uncalibrated accuracy drops below 95%"** 就是触发校准的警戒线。普通模型（Llama-3.3-70B、Qwen3.5）修复后是"ready to be **default**"；**MLA 模型不是**，被归类为"默认就需要校准、case-by-case 处理"。这不是偶发 bug，是 MLA 低秩结构的内在特性。

修复 Kimi-K2.5 的 MLA FP8 精度，靠的是**改 kernel 实现细节**（vLLM 的 Aiter MLA FP8 PS + CUDA Graphs PR），不是"加个校准"——说明这是需要专门工程投入的硬骨头。

### 8.4 澄清：那个"91%→13%"不是 MLA 的证据

初版（以及前几轮讨论）引用的"vLLM 上 MLA/DeepSeek FP8 从 91% 掉到 13%"**张冠李戴**。查证原文：

- 该数据出自 vLLM 博客 "The Problems We Found" 一节，是 **FlashAttention-3 FP8 kernel 在 Hopper 上的 FP32 累积精度 bug**，**与 MLA 无关**。
- 测试模型是 Llama-3.1-8B、gpt-oss-20b、Qwen3、Llama-3.3-70B，**无一用 MLA**。
- DeepSeek-V3 只是被引用为"训练时也遇到过同样硬件问题"（技术报告 Figure 7(b)）的旁证。
- **修复后**（two-level accumulation，参考 SageAttention2）精度恢复到 89%，且 Llama-3.3-70B 长上下文 AUC 恢复 97-98%，Qwen3.5-27B 在 1M context 完全恢复。

所以："91%→13%"是 kernel bug + 已修复，**不能用作"MLA 二次量化会崩"的证据**。MLA 的真实问题是 §8.3 的"consistent degradation + 需校准"，幅度 modest，但方向确定。

### 8.5 修正后的正确关系：执行 + 兜底

```text
模型原生层（MLA + block-scale FP8 / native recipe）
   ↑ 后端的主要职责：正确、高效地执行这一层
   │   （用对 kernel、用对 scale 粒度、修好 accumulation）
   │
后端介入的边界：仅当原生层无法满足运行时弹性时
   └─ 必须：outlier-aware / block-level 细粒度
      绝不能：per-tensor 粗压 latent
```

后端的价值不在"再压一次"，而在：
1. **正确执行**模型已定义的量化格式；
2. **调度和传输优化**（FlowKV 式正交收益）；
3. 仅在原生层确实不够时**谨慎兜底**，且用细粒度方法。

## 九、对商业落地推理团队的结论：MLA 二次量化不值得推荐

> 定调（用户提出，证据支持）：对强调商业落地的推理加速团队，在 MLA 模型上自创数值量化管线，不值得推荐。

### 9.1 可靠的精度恢复只有两条路，推理团队两条都难走

| 路径 | 对推理团队意味着 | 可行性 |
|------|----------------|--------|
| **PTQ + 校准** | 每个模型/硬件/workload 要单独校准；MLA 上证据显示校准后仍"consistent degradation"，不保证稳 | 脆弱 |
| **QAT（量化感知重训）** | 要重训模型——推理团队没有训练数据/recipe，成本巨大 | 基本不可行 |
| **等模型作者发 QAT 版** | 完全被动，节奏不由你控 | 被动 |

可靠的恢复（QAT）需要重训——这对推理加速团队意味着：要么自己重训（成本巨大、可能没原始训练数据/recipe），要么等上游（被动）。这正是"不值得推荐"的精确含义。

### 9.2 ROI 明确为负

对一个商业落地团队，做 MLA 二次量化的代价/收益账：

- **收益**：省一些显存/带宽（且 MLA 本身已经把 KV 压得很狠，边际收益小）。
- **代价**：
  - 精度不确定性（官方点名"consistent degradation"）；
  - 持续的 kernel/校准工程投入（修 Kimi-K2.5 靠的是改 kernel，不是加校准）；
  - 质量回归风险——长上下文检索这类场景对量化最敏感，正是商业用户最在意的；
  - 上游模型一更新（QAT 版、新 MLA 变体），自建压缩管线可能要重做。
- **结论：为边际的显存收益，赌一个不确定的精度和持续的工程成本，ROI 为负。**

### 9.3 推荐策略

在 MLA 模型上：
- **执行模型作者已定义的量化格式**（block-scale FP8 / native recipe），不自创压缩管线；
- **省资源靠调度、offload、batching**（FlowKV 式正交手段），不靠二次量化；
- 把工程投入放在**传输优化、调度、协议统一**这些确定有收益的方向。

### 9.4 ⚠️ 重要边界：不要过度泛化

被否决的是**"推理团队自己在 MLA latent 上加一层量化"**，不是"KV 量化"这件事本身：

| 场景 | 是否推荐 |
|------|---------|
| MLA + 推理团队自创数值量化 | ❌ 不推荐（本文结论） |
| MLA + 模型作者发布的随权重 recipe | ✅ 直接执行（不属于"二次量化"） |
| 普通 MHA/GQA + 标准 FP8 | ✅ 推荐（vLLM 官方"ready to default"） |
| 跨设备传输压缩（短生命周期，非 MLA latent） | ✅ 动态压缩的正当主场 |

**核心区分**：被否决的是"在低秩紧凑 latent 上叠量化"，不是"对所有 KV 做量化"。普通注意力（MHA/GQA）的原始 KV 空间冗余高，标准 FP8 是成熟、低风险、该用的。

## 十、分阶段落地路线（修正版）

| 阶段 | 内容 | 产出 |
|------|------|------|
| **P0 协议** | 定义带 `quant_level` + scale + layout 的统一格式 | 地基 |
| **P1 代价表** | 离线校准出逐层敏感度表（**部署方自建，非读模型**） | cost_i 可用 |
| **P2 决策器** | 贪心求解器 + 预算信号驱动 | 动态选择跑通（仅传输侧） |
| **P3 调度整合** | FlowKV 式负载调度，能避开的传输不压 | 正交收益 |
| **P4 执行优化** | deferred dequant + fused kernel / SmartNIC offload | 不干扰计算 |
| **P5 静态存储压缩** | 基于模型属性的静态量化，服务 prefix 复用 | 存储侧省显存 |
| **P6 原生压缩适配** | 正确执行 MLA/FP8 recipe，**不做二次量化** | 面向趋势不返工 |

注意 P2 明确限定为"传输侧"——动态决策的产物不进存储。P5 的存储压缩走静态路线。P6 的重点是"正确执行"，不是"叠加压缩"。

## 十一、决策判据与反模式速查

**四个一锤定音的判据：**

1. **"省下的资源是被全局重新分配，还是层自己留着？"** → 前者必须后端决策。
2. **"动态的动因来自模型内部还是链路/显存？"** → 后者决策在后端。
3. **"训练结束 bit 就固定了吗？"** → 是，则买质量卖弹性（进模型）；否，则弹性价值只能后端兑现。
4. **"这个压缩产物要存储复用吗？"** → 要，则决策必须基于模型属性（静态），不能基于系统状态（动态）。

**七个反模式（含本次新增）：**

- ❌ 把运行时选 bit 的逻辑放进 model forward。
- ❌ 假设 c6 免费可用（可能无原生硬件路径）。
- ❌ 传输一瓶颈就压缩（先用 FlowKV 式调度避开）。
- ❌ 忽略反量化干扰（ShadowServe 教训：解压 offload）。
- ❌ 异构 dtype 不定义协议就上 paged KV（破坏 prefix 复用）。
- ❌ **把动态压缩产物存进 prefix cache 跨周期复用（决策过期 + 状态污染）。** *(新增)*
- ❌ **在 MLA latent 上自创二次数值量化（精度风险 + 需 QAT 重训 + ROI 负）。** *(新增)*
