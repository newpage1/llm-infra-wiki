前缀复用是所有推理引擎都做的事，但**用什么结构索引已经算过的前缀**，三家给的答案完全不同。
这篇把三种放在一起看：它们要回答的是同一个问题，复杂度却落在不同的地方。

## 一句话对比

| | vLLM | SGLang | LMCache |
|---|---|---|---|
| 索引单位 | 固定大小的 block | 任意 token 边界 | 固定长度的 chunk |
| 索引结构 | 哈希表（块哈希 → 块号） | Radix 树 | 哈希表（链式 chunk 哈希 → 对象） |
| 命中粒度 | 块对齐（如 16 token） | token 级 | chunk 级 |
| 谁在用 | 引擎内的 %%BlockPool%% | 引擎内的 %%RadixCache%% | 引擎外的缓存层 |

差异的根源在第一行。索引单位和命中粒度是同一个决定：**哈希表只能按整块查，树可以按前缀查**。

## 三种结构各自的代价

### vLLM：把复杂度放在「块对齐」上

块号是固定大小的，所以一个请求命中的前缀长度必然是块大小的整数倍。
短于一块的复用做不到——这是为了换取块表的常数时间寻址。

块哈希需要**把前驱块的哈希也算进去**，否则两个不同的前缀会撞到同一个键。
所以这个哈希天然是一条链，改一个块会让后面所有的键失效。

### SGLang：把复杂度放在「树的分裂」上

%%RadixCache%% 用 Radix 树索引，命中可以停在任意 token 位置
（`python/sglang/srt/mem_cache/radix_cache.py:377` 的 `match_prefix`）。
代价是插入时要处理**一个节点只匹配上前半段**的情况——节点必须分裂，
分裂时 key 与 value 都要重新划分（`python/sglang/srt/mem_cache/radix_cache.py:437`）。

另外树要能淘汰，就得知道每个节点还被多少请求引用，
于是每个节点多了一份引用计数（`python/sglang/srt/mem_cache/radix_cache.py:238` 的 %%TreeNode%%）。
细粒度复用的代价就是这份额外状态。

### LMCache：把复杂度放在「链式哈希」上

LMCache 在引擎之外，它看到的是 token 序列而不是显存块，
所以它按固定长度的 chunk 切分、对每个 chunk 算一个**带前驱信息的**哈希
（`lmcache/v1/token_database.py:358` 的 `_prefix_hash`）。

它没有树，所以命中必须从第一个 chunk 开始逐段查——**查不到第一个就全不命中**。
好处是实现简单、可以跨进程跨机器共享同一套键。

## 什么负载下会先撑不住

- **块哈希**：前缀长度普遍小于一个块时，命中率会掉到 0。长系统提示词场景没问题，
  短对话反复改写开头就很差。
- **Radix 树**：节点数随「不同前缀的条数」增长，而不是随 token 数增长。
  大量互不相同的长前缀会撑大树，分裂与淘汰的开销也跟着涨。
- **链式哈希**：命中率对 chunk 长度敏感，且**跳过中间 chunk 的复用做不到**——
  只要有一个 chunk 对不上，后面全废。

## 待验证

上面关于「短前缀下块哈希命中率掉到 0」的说法是从块对齐推出来的，
